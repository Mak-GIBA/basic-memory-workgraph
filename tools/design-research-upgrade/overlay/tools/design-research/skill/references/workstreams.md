# 要件からコアロジックの研究テーマを切り出す

## 設計を担当する親と、個別研究の担当を分ける

upstreamは全体の目的・利用者体験・要件・システム境界を管理する親担当です。
全体を一度だけdesign-researchへ丸投げせず、要件達成に必要な能力へ逆算し、
その能力を左右する不確実な計算・判断処理を研究テーマ（work package）として切り出します。
切り出し自体はモデルによる内容判断です。この補助CLIは要件の意味や分割の科学的妥当性を自動判定しません。

基本順序は、ストーリー→懸念の確認→ユースケース→要件→必要能力→
コアロジック・技術的な問い→テーマごとのdesign-research→組合せの検証→design.mdです。
画面/API/DBの単位やライブラリ名で機械的に分割しません。

## 切り出すべき問いと、研究しないもの

各要件を research / standard / clarify / out_of_scope に分類し、根拠を記録します。
researchは要件を満たす方式が不確実なもの、standardは既存仕様・実装・検証で方式が十分定まるものです。
clarifyは利用者の懸念や受入条件が未解決なもの。新しい質問は既存の回答で解決できないものに限定します。
out_of_scopeは明示した対象外です。研究が必要な問題を標準実装に分類して回避しないことを内容レビューします。

一つの要件から複数のテーマが生じても、複数要件を一つのテーマが満たしても構いません。
個別に評価できないほど強く結びつくロジックは一つにまとめ、共通のロジックは重複調査しません。
判定基準は「この問いの答えにより、設計上の選択が変わるか」です。
標準的なCRUDや監査ログまで、比較研究と5候補を一律に要求しません。

## 例：検索品質と応答時間を改善する

| 要件 | 研究テーマ | 判断する問い | 観測するもの |
|---|---|---|---|
| 関連情報を見つけやすくする | RP1 候補抽出 | どの抽出方式なら関連情報の候補漏れを減らせるか | 候補段階のRecall、コスト、フィルター後の漏れ |
| 上位結果を適切にする | RP2 順位付け | どの順位付けなら関連結果を上位に出せるか | 順位指標、条件別失敗、追加推論時間 |
| 待ち時間を制約内に収める | RP3 計算配分 | RP1/RP2の組合せでどこを削減・キャッシュすべきか | 端から端までの応答時間、精度劣化、メモリ |

これは説明用の例であり、具体的な方式や数値を選定済みという意味ではありません。
各テーマで現行案・強い既存案・異なる原理の案を約5手法比較します。
**5はテーマ数でも合計の手法数でもなく、各テーマの候補数の目安です。**
意味のない候補で埋めず、少ない方が妥当なら理由を残します。アブレーションは候補数に含めません。

## 凍結する研究計画

親担当が `.specify/workbench/research-plan.json` に以下をまとめます。人向けの要点はrequirements.mdへ記載します。
新たな上流正本文書を増やすのではなく、機械用の計画とテーマ別report.mdを追加します。

- 正本要件のパス・SHA-256・全要件の分類と理由・対応テーマ。
- 各テーマのID、対象要件、検討理由、問い、範囲外、基準案、評価条件、検証計画。
- 固定する入出力・データ分割・指標定義などの契約IDと版。
- 研究上の依存関係と理由、並列実行の条件、占有資源、全体予算からの割当。
- 全体統合の担当、候補の組合せ確認、全体の受入条件、資源の総量、矛盾時の差戻し方針。

付属の実行可能な合成例はパッケージのexamples/workstream-demoです。
research_workstreams.py validate/plan/render は読み取りだけで動作します。

```bash
python3 <actual-design-research-skill>/scripts/research_workstreams.py validate   .specify/workbench/research-plan.json --project <project>
python3 <actual-design-research-skill>/scripts/research_workstreams.py plan   .specify/workbench/research-plan.json --project <project>
```

## 各テーマを実際の研究へ渡す

```bash
bash <actual-design-research-skill>/scripts/gan-harness.sh research   --project <project-or-isolated-copy> --slug <task-slug>   --requirements docs/upstream/requirements.md   --workstream-plan .specify/workbench/research-plan.json --workstream-id RP1   --reader-friendly --report-profile proposed-method --target-methods 5   --brief "RP1に対応する要件、固定入出力、候補抽出の比較と反証実験" --offline
```

ネット調査が許可され必要なときだけ既存の--allow-networkへ切り替えます。
原典未確認の主張、未測定の条件、仮説を区別します。新たな依存・課金・本番データ利用を自動許可しません。
既存法の選定だけならcomparisonプロファイルを使います。提案法を設計する場合はproposed-methodを使い、
独立した提案手法章、全体/詳細/既存法との差分図、数式/擬似コード、作用機序と限界を出力します。

## 並列にしてよい条件

アプリ実行時の処理順と、研究の依存関係を分けます。候補抽出→順位付けという実行順でも、
共通の固定候補セットを使う順位付け研究は候補抽出研究と並列に探索できることがあります。
ただし実際に選定した抽出結果との組合せ評価は、両方の結果が出てから行います。
依存先の出力を必要とする実験は、その出力を実行証跡とともに受け取るまで実施しません。
未測定の前提を埋めて依存を無視することは禁止です。

同じprojectでの複数ハーネスは既存のプロジェクト単位ロックで直列化します。ロックを削除・回避しません。
本当に並列で実行する場合だけ、親担当が許可済みの独立コピーを用意し、isolation=isolated-projectsとします。
各コピーの対象ソース版、正本要件、計画、評価セットを固定し、固有topicと資源上限を使います。
親だけが共通のrequirements.md/design.md/verification.mdを編集します。
コピーから戻すrun/report/実験資材はバイト列を変更せず、元のrun ID・版・パスの来歴を保存します。
出力パスが衝突した場合は上書きせず、統合を停止して新たなtopicでやり直します。

**この更新は並列可否と実行バッチの計画までを実装します。**
並列プロセス起動、コピー作成、実行資材の自動回収、総消費量の実時間計測は実装していません。
実行基盤の並列機能が使えない、資源が足りない、入力契約が固定できない場合は直列へ戻します。
CLIが返すwavesは完了結果ではなく提案順序です。親は実結果を確認してから次のバッチを実行します。
各runの既存上限は維持し、全体の検索・実験予算をテーマ数倍に自動増加させません。

## 統合し、全体のdesign.mdへ戻す

個別report.mdから、選定候補・比較条件・効く理由・根拠・入出力・必要資源・失敗条件・未検証を回収します。
局所的な最高精度を単に組み合わせず、接続互換性、精度×速度、メモリ総量、権限、データ鮮度を確認します。
全体ベースラインに対する組合せ評価をverification.mdへ登録し、未実行はplannedとして示します。
統合の矛盾が残る場合は関連テーマへ戻します。個別研究の完了だけでシステムの要件達成を主張しません。

`design.md`は、目的/具体例→研究テーマの分解図と対応表→全体アーキテクチャ→
各コアロジックの詳細図・手法・フレームワーク→組合せ・代表処理→検証と限界の順です。
研究の全文は複製せず、各詳細節から該当するrun固有reportへつなげます。
全体図の部品IDとテーマID・詳細図の部品を対応させて、初見でもどこを拡大した図か分かるようにします。
画面例は実際のUI/UX Skillへ渡し、調査対象のコアロジックと利用者の操作結果を接続します。

## 再検討と正確な状態の表示

要件変更では、変更した要件→関連テーマ→依存テーマ→統合評価の影響を先に分析します。
影響するテーマはreassessで旧案と離れた原理を再比較します。未変更の知見も適用条件を再確認して引き継ぎます。
現在の検査は正本要件全体のバイト列を固定します。そのため影響が小さくても、古いrunを
新しい要件の下で測定したかのように付け替えず、必要な再確認を新しいrunで記録します。
項目単位での自動差分判定・証拠の自動再利用は、この更新には含めません。

## v2の設計binding

新規/変更設計にはupstream-design-contract:v2とschema_version:2を使います。
既存v1の文書と承認は勝手に書き換えず、方式変更の際にレビューし直します。
JSONにはworkstream_plan{path,sha256}、各runのworkstream_id、既存のstate/reportとSHA-256/decisionsを記録します。
runのworkstream_contextはハーネスが入力を凍結して記録したものと一致する必要があります。
複数テーマの結果が一つのdesign_idに結び付く多対多の関係を認めます。
standard_decisionsはdesign_id、standardに分類したrequirement_ids、理由、実在するローカルevidenceを記載します。
これにより確定済みの標準設計へ不要な比較研究を強制しません。

integrationにはstatus(planned/verified/inconclusive)、rationale、selected_combination、tradeoffs、verification_ids、artifactsを置きます。
verifiedには実在する資材を必要としますが、ファイルの存在は測定の妥当性を証明しません。
uiuxの適用記録は従来どおり必須です。図・文章・要件の意味上の整合性と、研究が有効かどうかは別途レビューします。
