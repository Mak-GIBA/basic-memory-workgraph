## 設計前の必須研究・初見向け説明

`@ASSETS@/references/RESEARCH_FIRST.md`を読み、次の順を守る。
**ユーザーストーリー → 未解決の懸念の確認 → 使用感を考慮したユースケース → 検証可能な要件 → 必要能力とコアロジックの切り出し → テーマ別design-research → 組合せ検証 → design.md → 検証計画**。
既に回答のある懸念は再質問しない。回答のない重要な前提を推測で確定せず、仮説と合意を分ける。
新規/変更の実現方式を設計する場合、design-researchの使用は任意ではなく必須。対象の判断だけを精緻に比較し、単純なAs-Is転記や誤字修正に全体再研究を要求しない。
現行要件正本を`--requirements`で固定し、`--reader-friendly`を指定して実際のresearchまたはreassessを使う。
要件変更時は前回の完了研究と新要件からreassessを開始し、別原理の案も実験可能にする。
研究不能なら方式確定を止め、理由を報告する。自動インストール、権限拡張、アプリ本体の変更は禁止。

設計文書は目的/例/用語→全体アーキテクチャ→重要コンポーネント詳細→代表処理→フレームワーク/実装詳細の順に説明する。
各図にキャプション・読み方・矢印の意味を添え、全体図のどこを詳細図で拡大したか明示する。
新規/方式変更のdesign.mdにはupstream-design-contract:v2のmarkerと、研究run・正本要件・図解・UI/UX適用記録を含むbindingを追加する。
約5方式の比較、採用理由と限界をdesign.mdへ戻し、実行固有のreport.mdを参照する。研究全文は複製しない。
画面例は実在するooui-design等のUI/UX Skillを必ず適用し、主要/空/処理中/失敗/復帰の該当状態を説明する。
静止画の見栄えを実操作や使いやすさの実測と混同しない。設計依頼からアプリ実装や修正ハーネスへ進まない。
すべての要件・設計・検証文書に目的と読み方、具体例、図の意味、用語、未確認を含め、承認前に初見の読者の立場で読み直す。

## 要件駆動の研究分解（全体を丸投げしない）
`@ASSETS@/references/RESEARCH_WORKSTREAMS.md`を必ず読む。
要件から能力と不確実な計算/判断処理を逆算し、研究テーマ・要件ID・検証指標・入出力・依存関係を計画へ固定する。
画面/API単位では分けず、標準実装・要確認・対象外も理由付きで分類する。共通ロジックはまとめる。
約5手法は各テーマの比較目安であり、テーマ数を5に固定する意味ではない。
テーマごとに--workstream-plan/--workstream-idを付けてresearch/reassessし、独立コピーを使える場合だけ並列候補とする。
共通projectのロックは残す。親だけが全体文書を更新する。研究上の依存とアプリ実行順は別に定める。
最後に接続条件・組合せの品質/時間/資源を確認し、全体構成と各テーマの詳細を段階的に説明する。
v2 bindingに研究計画・テーマ別run・標準設計の根拠・統合評価の状態を残す。未実行を合格にしない。
