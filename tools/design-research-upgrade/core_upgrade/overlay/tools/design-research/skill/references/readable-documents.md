# 初見の読者に伝わる研究報告

## 読み手と説明順序

読者は対象プロジェクト・略語・前回の議論を知らないものとして書く。専門性を落とすのではなく、前提を足す。
最初に「誰が何に困るか」「今回何を比べるか」「何が分かり何が未確認か」を説明する。
1つの具体的な入力を使い、途中表現・分岐・出力を追ってから一般化する。
説明順は **課題 → 直感 → 全体図 → 各構成要素 → 数式/擬似コード → 検証 → 限界**。
用語は初出で定義し、同じ部品に図・本文・コードで同じ名前を使う。

## 図の契約

全体像と、重要な1部品の拡大図を少なくとも説明する。アプリが対象でなければ架空のサーバー/DB構成を作らない。
図にはタイトル、キャプション、矢印の意味、本文中の読み方、表示できない場合の説明を付ける。
図1の部品Xを図2で拡大したことを `parent_figure` と `expanded_component` に記録する。
一枚に全詳細を詰めず、概念図と実装図、学習時と推論時を区別する。図だけから性能を主張しない。
MermaidはMarkdown対応ビューアーで表示する。対応しない媒体ではSVG/PNGへ書き出し、実際に表示を確認する。
この更新は新たな外部レンダラーを導入せず、Mermaidの視覚品質や全構文の正しさは自動認証しない。
提案手法プロファイルでは既存の3種類のSVGを再利用し、同じ図を二重に載せない。

## reader_guide（dossierの追加フィールド）

`purpose, scope, takeaway, walkthrough, glossary, limitations` は説明文。
比較は約5方式を基本とし、より少ない候補が妥当な場合は`comparison_exception`に実質的な理由を記載する。数合わせをしない。
`diagram_source` は `reader-guide` または `proposed-method`。
後者は検証済みの提案手法章の図を参照し、`figures: []` とする。
前者の `figures` は2–6枚。各図は次を持つ。

```json
{
  "id": "F1", "kind": "overview", "title": "全体処理",
  "caption": "入力から出力までの設計案。性能を実測した図ではない。",
  "reading_guide": "左の入力が処理を経て右の出力になる。",
  "alt": "入力 → 処理 → 出力。",
  "nodes": [{"id": "Input", "label": "入力"}, {"id": "Core", "label": "処理"}],
  "edges": [{"from": "Input", "to": "Core", "label": "対象データ"}]
}
```

`detail`図は `parent_figure: F1, expanded_component: Core` を加える。
雛形の図をそのまま最終成果物として出さず、対象固有の中間表現と境界条件を記述する。
構造検査成功は内容の科学的正しさ・読者理解・実行済み性能の保証ではない。

## 完了前の読み直し

専門用語を知らない読者が、目的、部品の責任、処理の流れ、採否の理由、未検証事項を説明できるか点検する。
読みやすくするために証拠・適用条件・失敗結果を削らない。生成後の確定レポートは書き換えず、ロールの説明フィールドを改善して再生成する。
