# OOUIからアプリを設計・実装する

ユーザーの目的を、対象とそれに対する操作へ整理してから画面を作る。
OOUIへの適合、機能の充足、表示の品質、操作の完了をそれぞれ確認する。
現在の依頼、既存仕様、利用者、デザインシステムを優先する。

## 設計から実装へ

1. **目的と必須機能を確認する。** 利用者、頻度、主な作業、既存の制約を読む。
   プロジェクトの起動・テスト方法も確認する。発見できる情報を毎回質問しない。
   利用可能なBasic Memoryの過去の指摘を、[共通レビュー基準](references/review-policy.md)の
   手順で検索して読む。今回の目的・利用者・制約に合うものを設計と確認へ反映する。
2. **対象を整理する。** ユーザーが選ぶ・比較する・変更する対象を挙げ、属性、関係、
   操作を分ける。要件中の名詞やDBテーブルをそのまま画面にしない。
3. **ビューと経路を決める。** 一覧・検索結果などの集合と、1件の属性・操作を扱う詳細を
   対応付け、関連対象へ移れるようにする。新規作成は集合、編集・削除は行や選択した
   対象、一括操作は選択した集合に結び付ける。不要な専用画面を増やさない。
4. **操作と状態を決める。** 作業途中の対象切り替え、入力保持、戻る、中断と再開、
   空状態、処理中、成功、失敗を扱う。対象が固定の手続きはタスク起点も検討する。
5. **認知負荷を点検する。** 覚える、探す、比較する、対応付ける、推測する、行き来する
   作業を画面がどこまで支援するか確認する。必須情報と主要操作を見つけやすくし、
   説明の追加、機能の隠蔽、操作数の削減だけを改善とみなさない。
6. **見た目を設計して実装する。** ここまでの短い設計メモをデザイン・実装へ渡す。
   既存の技術構成とデザインシステムを使い、タイポグラフィ、余白、色、状態表現、
   レスポンシブ表示を揃える。必須機能を見た目だけのボタンで済ませない。
7. **実画面と操作を確認する。** 必須フローと状態をブラウザーで操作し、結果の画像を
   見る。必要な既存テストを実行する。未実装、仮応答、未確認を区別して報告する。

設計メモには、対象・主な属性・関係、集合と詳細、操作の対象、状態保持、必須機能と
確認フローを残す。対話内の短い表でもよい。既存仕様があれば再利用し、軽微な修正で
設計書一式を新設したり、アプリ全体を再設計したりしない。

## 使い分けと詳細

- 対象抽出、検索、一括操作、固定手順、Mobileの設計は
  [OOUIの設計判断](references/ooui-modeling.md)を読む。
- 情報構造、フォーム、文言、状態、画面の密度を決める際は
  [認知負荷のTips](references/cognitive-load.md)の該当項目を読む。
  新規・大幅な構造改善では6分類を一通り確認する。
- 実装・完了判定では[品質と検証](references/quality-gates.md)を読む。
  設計だけの依頼では実装やハーネスを起動しない。
- 既存アプリのレビューでは、起動方法等を確認した後、実画面を先に観察する。
  [共通レビュー基準](references/review-policy.md)に沿って、操作と画像を根拠に判断する。
- 考え方の出典と解釈の範囲は[出典](references/sources.md)にある。

## インストール済みスキルとの連携

- **Product Design / Build Web Apps**：先に上記の画面構造を決め、設計メモを画像生成や
  デザインの入力に含める。対象、関連、必須機能、情報の優先順位、必要な状態を保つ。
  ビジュアルの探索・承認・実装手順は各スキルに従う。承認済みデザインと必要な機能が
  両立しない場合は具体的な差異を示し、変更範囲を確認する。
- **yomiyasu**：日本語UIのラベル、説明、空状態、エラー文に加え、設計メモやレビュー・
  改善レポートの下書きにも、利用可能なyomiyasuを読んで一度推敲することを推奨する。
  主張、対象名、専門用語、数値、ID、条件、確認結果、根拠と断定の強さを保ち、
  短いラベルを長文化しない。UIラベルを文章の文字数・文末のノルマに合わせない。
  未導入なら必要な文言確認を続け、別の `install_codex_yomiyasu.sh --apply` を案内する。
  このスキルから導入や設定変更を行わない。
- **Basic Memory**：設計・レビューの前に、関連する過去の指摘とその適用範囲を参照する。
  今回の依頼と実画面・操作を優先し、参照したノートと適用理由は既存の設計メモや所見に
  短く残す。未導入・参照不能・該当なしの場合も作業を続ける。参照手順は読み取りのみ。
- **web-design-guidelines**：実画面で見つかった問題のコード確認と、ラベル、フォーカス、
  コントラスト等の実装確認に使う。コードを読んだだけで操作を検証済みにしない。
- **ux-gan-harness**：画像付きレビューや修正反復が依頼の範囲にある場合、実装済みの
  アプリとURLを渡して実際のBashハーネスを使う。レビューだけは `audit`、修正は `run`。
  新規実装では、依頼の範囲で必要なブラウザー確認を行い、ハーネスで再確認する際は
  適用するスキルを読む。`UX_GAN_CHILD=1` の子実行では再起動しない。
  ハーネスが利用できない場合は、実施した直接の確認と限界を報告する。

スキルやインストーラーの整備依頼は、別のアプリの作成・修正を許可しない。
