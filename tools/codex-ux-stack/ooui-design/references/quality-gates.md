# 品質と検証

## 設計と実装で確認するもの

| 対象 | 確認すること | 根拠 |
|---|---|---|
| 必須機能 | 要件の機能が実際に利用でき、結果が反映される | 要件とフローの対応、操作結果、既存テスト |
| OOUIと使い分け | 対象、属性、操作、関連、現在地が分かる | 画面と遷移。固定対象・固定手順は採用理由 |
| 認知負荷 | 不要な暗記、推測、探索、比較の往復、再入力を減らせる | 同じフローの前後の画像・操作記録 |
| 見た目 | 情報階層、文字、余白、色、部品、状態表現に一貫性がある | 実際の表示。画像コンセプトを使った場合は選択済みデザインとの比較 |
| アクセシビリティ | ラベル、読み上げ名、キーボード、フォーカス、コントラストを確認する | 実操作、アクセシビリティ情報、必要なコード確認 |
| 状態 | 空、処理中、成功、入力不備、失敗、取消、戻る、中断の該当状態を扱う | 実操作と結果。存在しない状態は適用外として理由を残す |

## 画面と操作の確認

1. 起動方法、URL、必須チェック、テストデータを確認する。
2. 対象の画面を撮影して見る。各操作を選ぶ際も画面を見てから操作し、結果の画像を見る。
   コードは、観察した問題の調査・修正に使う。
3. Desktop、Tablet、Mobileで必須フローを完了する。ハーネスの基準は1440×900、
   768×1024、390×844。既存の対応範囲や案件の要件がある場合はそれも確認する。
4. 観察した画面、対象、操作、状態を記録する。単にクリックできたことと、目的の結果へ
   到達したことを区別する。必要な既存テストを実行する。
5. 修正した場合は同じフローを再実行し、情報の発見、判断、操作、状態保持が悪化して
   いないか確認する。安全な確認や意味の分かるラベルの追加を、増加数だけで否定しない。

UIだけの試作が依頼なら、ダミーデータや仮の状態管理を明記してその範囲で確認する。
実サービスとの接続が要件なら、見た目だけの操作や仮応答で完了としない。
今回の設計のために、未依頼のバックエンドや新機能を勝手に作らない。

## ハーネスとの連携

`ux-gan-harness`が利用可能で、レビューや修正が依頼の範囲にある場合はそのスキルを読み、
実際のBashを使う。レビューだけは `audit`、修正は `run`。修正役の申告だけで解消済みに
せず、別の評価実行で結果の画像と操作を確認する。

ハーネスの出力では、OOUIの判断を `screen_reviews.information` / `interaction`、
認知負荷を `friction`、文言を `copy_issues`、前後の負担を `simplicity` に記録する。
意味のある障害は `issues` に原因・改善案・根拠を付け、主要フローを妨げるものは
重要度と `friction.blocking` に反映する。適用外の判断も画面の所見に理由を残す。

`step_count`は代表フローと数え方を説明して記録し、`decision_points`は実際に選択が
必要な箇所を数える。往復や再入力等は操作記録と所見に対応付ける。頭の中の負荷を
計測した数値や、人間の満足度として扱わない。

重大問題、必須フロー、該当状態、必要なチェック、画像、修正による悪化を確認する。
OOUIのチェック項目が揃ったことだけでは機能や表示の完成度を保証しない。
[記事の検証](https://zenn.dev/emuni/articles/ooui-agent-skill)も構造の変化と機能・完成度を
区別している。AIの所見、機械的な検証、人間によるユーザーテストを分けて報告する。
