# SpecKit Upstream Workbench

## 入口
共通CLI: `@COMMAND@`。共通資材: `@ASSETS@`。
これは独自の上流文書運用プロファイルであり、ECC、Basic Memory、Codex Hookではない。
他の設定や実装を勝手に変更せず、現在のユーザー指示を優先する。

1. 現在のプロジェクトのルート、システムID、対象範囲、作業モードを確認する。
2. CLI `doctor --project <root>` と `paths --project <root>` を確認する。
   未導入なら `attach --project <root> --system <ID> --mode <mode>` で計画を提示。
   ユーザー承認後だけ `--apply` を使う。既存文書と重複する場合は既存正本を優先する。
3. `prompt --project <root> --mode <mode>` の出力を読み、
   `@ASSETS@/references/METHOD.md` と `TRACE_FORMAT.md` を読む。
4. 最初に調査計画、必要な根拠、作成・変更予定文書、確認すべき不明点を提示する。
   「仕様整理して」はソース・DB・デプロイ変更の承認ではない。

## 全モード共通の成果物
システムの目的・スコープ・関係者・業務シナリオ・ユーザー価値を先に整理する。
要件は機能・品質・データ・インターフェース・運用・制約に分ける。
ユーザーストーリーを画面/API/DBという技術作業だけに分けない。
要件が規定する必要な振る舞いと、設計が選ぶ実現方式を区別する。
各項目にシステムID、固有ID、根拠、状態、上位項目・設計・検証への関係を持たせる。
仕様正本はMarkdown。```upstream のJSONは同じ項目のメタデータ。索引は生成物。

## SpecKit公式Skillとの連携
既存の .agents/skills/speckit-*/SKILL.md を実際に確認して使う。存在しないコマンドは呼ばない。
new/change: constitutionの合意事項確認 → specify → clarify → plan → tasks → analyze。
existing: As-Is、合意済み仕様、To-Beを分離。調査結果から仕様案を作る。再実装しない。
bug: bug-assessで再現・期待挙動を整理。欠けた上位要件は要確認として残す。
refactor: 非変更条件、改善する品質目標、互換性、移行・切り戻しを上位へ結び付ける。
独立した不具合でもシステム目的・対象要件への参照を省略しない。ただし上流文書全体を毎回作り直さない。
実装/bug-fix/DB変更/deployは別途明示承認があるまで進まない。

## 既存要件・実現方式の見直し
existing/check/change/refactor/bugでは `@ASSETS@/references/REASSESSMENT.md` を読む。
要件の妥当性、精度の評価方法、実現方式の効果を分けて確認する。
判断を左右する技術的な不確実性があれば、Design Researchの使用理由とresearch/auditを明示し、実際のSkillを読み、gan-harness.shを実行する。
入力・比較条件・実行不能時の扱い・仕様への反映は同資料に従う。単純な文書修正には研究を一律要求しない。
研究の終了コードから採用承認を作らず、上流整理からrunによるアプリ修正へ進まない。

## 要件工学・検証
単一の要求に複数の独立した義務を混ぜない。曖昧な数値を推測しない。
権限、無効入力、API失敗、タイムアウト、再試行、重複・並行処理、部分保存、再起動・復旧、監視を検討。
該当しない条件は対象外の理由を残す。テスト計画は必須だが、テスト未実行をPASSにしない。
文書承認とアプリ検証を混同しない。ユーザーの沈黙を承認とみなさない。
ローカルのコード版と稼働中の版の一致を確認できなければ不明として扱う。

## 終了前
`check --project <root> --phase draft` で構造を確認する。
人による合意・設計・検証計画が揃った段階で `--phase ready` を使用する。
`trace --project <root> --write` で内部の関連索引を更新する。
既存非標準文書は `register-doc` で登録できる。本文を勝手に移動・削除しない。
参照があるだけで意味が正しいとみなさず、人向けの矛盾・曖昧さレビューもする。
最終回答は、目的と対象範囲、更新文書、未決定事項、承認待ち、実施/未実施の確認を短く提示する。
`@ASSETS@/references/ARTIFACTS.md`を読み、要件・設計・検証の該当する正本と、研究を行った場合のreport.mdだけを通常の確認先として案内する。
新規は3文書にまとめ、既存の旧形式は任意のmigrateまで保持する。内部JSON・台帳・生ログは調査に必要な場合だけ補足する。
日本語の文書を仕上げる際は、利用可能なyomiyasuを使う。

## 定型コマンド（長い初期指示が不要）
- $upstream-new: 新規アプリ/機能の上流資料。
- $upstream-existing: 稼働中システムをAs-Is/合意済み仕様/To-Beに分けて整理。
- $upstream-change: 仕様変更の影響分析と上流更新。
- $upstream-bug: 不具合の対象要件・再現条件・修正/回帰計画。
- $upstream-refactor: 非変更条件・品質改善・設計変更の上流整理。
- $upstream-check: 構造と内容のレビュー。
各コマンドはグローバルSkillであり、SpecKit公式の同名コマンドを上書きしない。
ユーザーの依頼に対応する固定モードのflowを読み、成果物を具体化する。
ready確定を報告するときは CLI gate --project <root> --write を実行する。
gate --verify は後日の変更・追加・削除で古くなった記録を拒否する。
