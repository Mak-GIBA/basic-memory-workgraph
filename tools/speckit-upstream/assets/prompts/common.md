新規の標準成果物はrequirements.md（要件）、design.md（設計）、verification.md（検証）の3文書です。
各文書は結論・確認してほしいこと・未確認を先に書き、関連する詳細を節にまとめます。文書の項目は固有のupstream:section内に置きます。
Researchを実行した場合は1本のreport.mdを参照し、採用理由を設計、確認条件と結果を検証へ戻します。報告の全文を複製しません。
既存の旧形式は明示したmigrateでだけ移行します。公式のspec.md/plan.md/tasks.mdは必要な詳細として保持します。
日本語の要件・設計・検証文書、研究・レビュー報告の下書きには、利用可能なyomiyasuを読んで一度推敲することを推奨します。
主張、専門用語、ID、数値、条件、確認結果、根拠、断定の強さ、upstreamメタデータ・リンク・引用を保持します。
レビュー・承認前に本文を仕上げ、承認済み本文の変更は通常の再レビュー手順へ戻します。固定済み資料・生ログは保持し、未導入でも執筆と文書確認を続けます。

このプロジェクトでは、全作業モードで共通の上流文書体系を維持してください。

最初に現在の目的・スコープ・関係者・既存仕様・設計・テストと、この依頼の対象を確認してください。
上流文書がない場合は調査計画から始め、分からない目的や合意事項を推測して確定しないでください。

整理順は、目的 → 関係者の要求 → 利用シナリオ/ストーリー → 検証可能な要件 → 仕様/設計 → 検証計画です。
上位と下位を一対一に押し込まず、多対多の関係を固有IDで表現してください。
非機能、インターフェース、データ、運用、制約を独立に検討してください。
現状の観測・過去の合意・改善案を区別し、根拠、対象版、確認日、不明点を残してください。

まず調査・整理計画を提示してください。承認後は文書作成・整理までを進め、
ソース変更、DB変更、破壊的テスト、本番アクセス、デプロイは別途明示承認があるまで行わないでください。
既存要件・方式の見直しで必要なresearch/auditは、依頼と既存の許可に含まれるローカル調査・隔離した検証/PoC・研究報告までを扱います。REASSESSMENT.mdに従い、アプリのソースや本番データは変更しません。
ECC・Basic Memory・既存Hook・AGENTS.mdは変更しないでください。

上流項目の合意は、文書を書いたこと自体では成立しません。
設定されたapproval profileに沿って `$upstream-review` でレビュー対象を固定し、
ユーザーが具体的IDを明示承認した場合だけ `$upstream-approve` でhash-bound approvalを記録してください。
レビュー後に本文や上位依存が変わった場合は古い承認を再利用せず、再レビューしてください。

要件・設計・検証の対応をupstreamメタデータに記録し、構造検査と対応表生成を行ってください。
構造検査の成功、ユーザー合意、意味上の妥当性、実テスト成功は別として報告してください。


## 文書の確認条件
- 全体READYを主張する前に、目的・ニーズ・ストーリー・要件・設計・検証計画の範囲があるか確認する。
- need/storyが本当に対象外なら、架空の要求を作らず、TRACE_FORMAT.mdのreadiness_exemptionsに従いgoalへ具体的な省略理由を記載してユーザーの合意を取る。
- 通常のMarkdown本文も承認対象に含まれる。明示した節はその節の項目に、節外の共通条件は文書内の全項目に結び付く。旧形式の節のない文書は文書全体を固定する。
- 旧版の承認は自動移行しない。新しいレビュー資料を提示し、ユーザーが承認した対象だけ再承認する。
