# 成果物の確認先

新規プロジェクトでは、次の4種類を読む。実際の`docs_dir`・slug・run IDを解決し、今回存在するファイルだけ案内する。

| 確認したいこと | 正本 | 主な内容 |
|---|---|---|
| 何を作る・維持するか | `docs/upstream/requirements.md` | 目的・利用者・範囲、機能・品質・制約、現状と期待、不明点 |
| どう実現するか | `docs/upstream/design.md` | 構成・動作・データ・API・運用、選定理由と変更影響 |
| 何を確認し、どこまで確認済みか | `docs/upstream/verification.md` | 受入条件、確認方法、実際の結果、未実行、証拠 |
| 研究・実測から何が分かったか | `docs/design-research/<slug>/report.md` | 結論、比較、検証、変更前後、残る確認。実行した場合のみ |

各文書は「結論と確認してほしいこと → 詳細」の順に書く。ID、数値、対象版、根拠、断定の強さを保持する。
新しいADR・不具合一覧・質問一覧・修正報告を標準成果物として別々に増やさず、該当する文書の節を更新する。
日本語の要件・設計・検証文書、研究・レビュー報告の下書きには、利用可能なyomiyasuを
読んで一度推敲することを推奨する。ID、数値、条件、確認結果、根拠と断定の強さ、
メタデータ・リンク・引用を保ち、レビュー・承認前に本文を仕上げる。
承認済み本文を変える場合は再レビューし、固定済み資料・生ログは保持する。未導入でも執筆を続ける。

## 内部記録と詳細参照

CLIの承認チェックポイント数は文書数と別。対象IDの明示承認と依存の検査を維持する。
レビューのスナップショット・承認要約・trace JSON・gate・台帳は`.specify/workbench/`に保存する。
レビュー依頼では、該当する節へのリンク、対象ID、判断待ちを先に示す。固定済みpacketのMarkdownリンクは1つ添えればよい。JSONや台帳を毎回列挙しない。
承認の記録は`approval-plan`で現在の状態を確認する。本文、共通条件、依存が変わった場合は古い承認を使わない。

Researchの機械用記録は`.internal/`、実行・生ログ・証拠・保存版は`runs/<run-id>/`に残る。
最新の`report.md`の冒頭で実行ID・状態・停止理由を確認する。停止前にも今回の状態を表示する。
長期参照には`runs/<run-id>/reports/report.md`と、その報告内の証拠リンクを使う。
設計には採用の理由・条件・関連IDを要約し、検証には評価条件と実際の結果を戻す。研究の全文は複製しない。
SpecKit公式の`specs/<feature>/spec.md`・`plan.md`・`tasks.md`は必要な機能詳細の参照先として保持する。

## 旧形式

`.specify/workbench.json`に`document_layout: compact-v1`がないプロジェクトと、Researchの`.internal/layout.json`がない既存の旧資料は従来の配置を維持する。
インストーラーの更新やattachの再実行だけでは移行しない。既存の正本を案内し、旧形式を新規の標準として増やさない。
任意移行は`migrate --project .`で内容・リンク変更・再レビュー対象を確認し、`--apply`で適用する。
Researchは`gan-harness.sh migrate --project . --slug <topic>`を使う。移行元と設定をバックアップし、承認は再付与しない。

## Skill実行後の回答

結論、今回の変更、判断待ち・未実行を短く伝え、関係する主資料へのリンクを付ける。
3文書を作った場合は最大3行、研究も行った場合は報告の1行を加える。「読む場所 / 今回の確認箇所」で十分。
内部記録は、その検査の調査や承認の固定に必要なものだけ補足する。未作成の資料・未実行の確認は成功と表示しない。
