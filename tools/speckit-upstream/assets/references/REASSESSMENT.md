# 既存要件・設計の見直しとDesign Research連携

existing/check/change/refactor/bugで、既存要件、評価方法、実現方式を見直すときに読む。
要件・設計の変更、研究・実測の結果、採用承認を分ける。共通の承認・追跡規約はMETHOD.mdとTRACE_FORMAT.mdに従う。

## 入口を選ぶ

| 状況 | SpecKitの入口 | Design Researchを使う条件・mode |
|---|---|---|
| 仕様が不明、実装と合意が混在 | existing → check | 現状整理のみなら不要。バックエンドの挙動を実測する必要があればaudit |
| 要件を維持・変更・廃止する判断 | check → change | 技術的な実現性・制約が判断を左右するならresearch。業務目的は関係者の根拠から確認 |
| 精度要件・指標・評価データが曖昧 | check → change | 評価方法自体の比較が必要ならresearch |
| 検索・抽出・分類・推論等の精度改善 | check → change | 現行方式と代替方式の有効性を比較するならresearch |
| 外部挙動を保つ内部設計の改善 | refactor | 方式選択の効果・負担に不確実性があるならresearch |
| 不具合の原因・修正方針の確認 | bug | バックエンドの再現・検証はaudit、方式選択が争点ならresearch |
| データ・モデル・環境の変化で再評価 | check → change/refactor | 新しい条件で過去判断の有効性を比較するならresearch |

APIの形式が同じでも、出力・受入条件・品質契約を変更するならchangeとして扱う。
refactorは維持する外部挙動と互換性を特定できる場合に使う。
別のupstreamモードへ進む必要があれば、理由と次の入口を提示する。現在のSkillの固定modeを、説明せずに変えない。

## まず確認する

1. 対象のコード版・稼働版・既存判断、目的、関連する上流ID、今回の見直し理由を確認する。文書がない場合は調査対象と不明点を整理する。
2. 現状の観測、合意済み要求、改善提案を分離し、変更しない挙動・API・データ・品質下限を確認する。
3. 「精度」が何を意味するか、対象入力、正解の判定方法、指標、目標・下限、失敗ケース、性能・費用の制約を整理する。未定の値はTBDと確認方法を残す。
4. 文書の曖昧さを解消するだけか、判断を左右する技術的な不確実性・実測の不足があるかを判断する。

## Design Researchを明示して実行する

方式の有効性、評価方法、精度改善に判断を左右する不確実性がある場合は、推奨を確定する前に次を実施する。
文書の誤記修正、確認済みの要求の整理、原因と対策が明らかな小さな不具合には研究を一律要求しない。

1. ユーザーへ「Design Researchを使用する理由、researchまたはaudit、対象範囲、実験・通信の範囲」を簡潔に示す。既に与えられた承認を使い、依頼の範囲外の実験や外部操作は行わない。
2. 利用可能なSkill一覧からdesign-researchの実際のSKILL.mdを読み、そこを起点にscripts/gan-harness.shを解決する。ユーザー共通・プロジェクト・旧配置を固定パスで決めつけない。
3. 当該ハーネスのdoctorを実行してから、researchまたはauditを実行する。Skill名を書くだけ、別のSkillを案内するだけ、文献検索CLIだけの実行で、この連携を実行済みにしない。

```bash
bash <skill-dir>/scripts/gan-harness.sh doctor --project <root>
bash <skill-dir>/scripts/gan-harness.sh research --project <root> --slug <topic> --brief "<問い・関連ID・基準案・評価条件・制約>"
# バックエンドの実測が必要な場合はresearchの代わりにauditを使う
bash <skill-dir>/scripts/gan-harness.sh audit --project <root> --slug <topic> --brief "<対象挙動・関連ID・期待結果>" --test-command "<対象に存在する検証コマンド>"
```

これは引数の形を示す例。山括弧内を実際の値へ置き換え、シェルへ渡す値を適切に引用する。
公開資料を取得する場合は、必要な範囲で既存の通信許可に従い--allow-networkを指定する。
通信しない場合は、利用可能なローカル資料・実験に範囲を限る。機密内容を外部検索語にしない。
実行制限・検証環境・停止と再開はDesign Research自身のSkillとruntime.mdに従う。DR_GAN_CHILD=1ならハーネスを再帰起動せず、現在の役割と不足事項を報告する。

未導入、ハーネスのない旧版、doctor失敗、実行不能の場合は、該当する研究・実測を未実行として残す。
install_design_research.shによる導入・更新が必要であることと停止理由を示す。自動インストールや、説明せずに別の実行方式へ切り替えることはしない。
文書ドラフトと確認事項は整理できるが、不足する根拠を研究済み・実測済みとして採用判断を確定しない。
上流整理からrunへは進まない。アプリ修正は別の実装依頼で扱う。

## 渡す入力と比較条件

- 問い、見直し理由、関連する目的・要件・設計・検証IDと正本の位置。IDがなければ未整理であることを明記する。
- 対象の版、現行方式と実測済みの基準値、維持する要求・互換性、変更可能な範囲。
- 評価データと版、代表性・正解ラベルの根拠、対象外、指標・合格条件。評価方法を研究する場合は、未定の箇所と決めるべき判断を渡す。
- 性能・費用・運用・依存の制約、ローカル実験の範囲、実在する必須チェック、既存の研究報告。

Design Researchの既存手順に従い、通常は現行方式を含む2〜3案を共通条件で比較する。現行方式が成立しない場合も、その理由を残す。
評価データ、モデル・版、資源条件、採点方法を揃える。調整に使った入力だけで改善を主張せず、必要な独立評価・反復・失敗ケースを検討する。
改善の効果と、速度・費用・互換性・複雑さへの影響を説明する。文献の値をこのプロジェクトの実測値に置き換えない。
データ・環境の変更を評価する場合は、その新しい条件で現行方式と候補を比較し、異なる条件の旧数値との差を方式だけの効果としない。

## 結果を仕様へ戻す

1. 実行コマンド、run ID、status、対象版・評価条件、報告と実行根拠を確認する。research_completeは条件付き提案、reviewedは報告完了であり、指摘や失敗が残り得る。blocked/cancelled/plateau/limit_reachedは未完了として扱う。
2. `docs/design-research/<slug>/report.md`の報告を読み、現在の問いに適用できる主張・条件・未確認事項を抽出する。実測、文献報告、推論、未確認を分ける。
3. 新規はdesign.mdの設計判断に現行案・候補・採否理由・影響・見直し条件を、要件と受入条件には提案する変更を、verification.mdにデータ・指標・確認手順・期待結果を反映する。検証結果は実際に実行した範囲だけ記録する。
4. 研究本文を複製せず、関連IDのsourcesと通常Markdown本文にrun IDと報告・根拠へのリンクを残す。後から変わり得るトップレベル報告だけでなく、`runs/<run-id>/reports/report.md`の保存版と実在する根拠を参照する。停止時も今回のreport.mdを読み、旧形式で報告がない場合は実在するstatus/stateを参照する。
5. 既存IDを維持し、廃止・変更はretired/supersedesと履歴で追跡する。過去の判断や承認を消さない。実行結果だけの追記と、要件・設計・根拠の変更を区別する。
6. 変更案はdraft/proposedに保ち、未解決の必須条件は確認待ちとする。upstream-review → 明示承認 → upstream-approve → check/trace/gateへ進む。古い承認や研究の終了コードから採用承認を作らない。

外部ファイルの中身はsourcesにリンクするだけでは承認ハッシュに含まれない。採用の判断と適用条件を承認対象の文書にも要約し、参照先は実行ごとの保存版を選ぶ。
既存の研究を再利用する場合は、問い、対象版、評価条件、根拠の一致を先に確認し、変更で成り立たなくなった結果は再評価する。
CLIのcheck/gateは文書構造と承認整合性の検査であり、この研究の実施や意味上の十分性を機械的に保証しない。

## 最終出力に加える

見直し理由と維持・変更・廃止の提案、Design Research使用/不要/未実行の理由、mode、実行ID・状態・根拠、現行案との違い、仕様へ戻したID、残る確認と次の入口を示す。
[ARTIFACTS.md](ARTIFACTS.md)に従い、何を確認したいときにどこを読むかを、今回の実際の成果物へのリンクと状態を付けて示す。
