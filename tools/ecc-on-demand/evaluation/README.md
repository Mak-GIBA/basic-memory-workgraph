# ECC MCPの導入判断に使う測定

インストーラーからは実行しない明示的な比較実験です。入力と正解は各contractに固定し、実測した最終回答、実際のMCP呼び出しの有無、所要時間をresultsに保存しています。推論ログや認証情報は保存しません。

同じ課題に対し、既存ツールを使う基準案と、その課題に対応するMCPを使う案を比較します。用途が違うMCPを全課題に使わせる順位付けは行いません。統合検証用のcandidate A/Bはこの二つの方針を指し、課題群ごとの内訳を判断に使います。Chrome DevToolsはブラウザー課題の追加比較です。

主要指標は推論・文書解釈の最終回答の正答、ファイルから取得できた重要値、操作後のDOM値です。応答量や起動成功は精度の代理にしません。推論の常用採用条件は、誤りを増やさず正答を少なくとも1件増やし、平均処理時間の増加を10%以内に収めることです。この条件はreasoning-contractで事前固定しました。

`measure_reasoning.py`は通常のCodex認証でgpt-6.1-sol/maxを使い、6問を各条件2回測ります。順序を入れ替え、MCPの呼び出しが成立したかも確認します。`measure_documentation.py`は公式文書直接取得とContext7の取得文書を同じ2問・モデルで解釈します。既知URLでの1回の比較なので、未知の文書を探す能力の一般評価には使えません。

`measure_tools.py`は合成文書の4ケースとローカルHTMLの2ケースを各2回実行します。ファイル課題は決定的な抽出器で情報取得を採点しており、モデルの推論精度は測っていません。ブラウザーの最終DOM値は比較できますが、nativeの操作区間とMCPの移動・操作区間の計測範囲が異なるため、時間比を一般的な速度差と解釈しません。返却バイト数は課金トークン数ではありません。

新しい会話で共有キャッシュに依存するとToken Optimizerが「変更なし」だけを返し、5項目とも取得できない失敗を残しています。同一会話の再読では過去の本文を利用でき、返却量を減らせます。新しい会話では`diffMode:false`による全文取得で値を回復しました。欠落時に成功扱いせず、条件の違いを含めて判断します。

`evidence/pilot/`は測定準備の失敗を含む別記録です。MCPが呼ばれなかった推論試行、古いツール名・pageIdの指定、DOMのtextContentを関数として扱った誤りを本試験の成績へ混ぜません。最後の修正後の本試験ではMCPの実呼び出しと最終DOM値を取得できました。

保存データは`check_captures.py`で再採点できます。ネットワークやモデルを使わず、保存された最終出力を固定正解と比較し、hash・入力・実呼び出しの記録も照合します。インストーラー改修後の[GAN harnessの限定audit](../../../docs/design-research/ecc-mcp-installer-validation/report.md)でも、47テストと26組の再採点が成功し、独立レビューが完了しました。外部モデルや公開サーバーを再実行した結果ではありません。少数の合成課題であるため、一般的な性能改善や人間の作業時間の短縮を推定しません。

```bash
# リポジトリのルートから、保存された出力を再採点する
python3 -B tools/ecc-on-demand/evaluation/check_captures.py
```

再測定にはNode依存パッケージの実体、ブラウザー、モデル利用が必要です。モデルを呼ぶスクリプトは通常のCodex利用量を消費します。テストスイートやインストール時に自動実行しません。
