# 使い方

[docs一覧](../README.md) · [概要](README.md) · [導入手順](installation.md) · [記録方針と検証](behavior.md)

## 普段の言葉で依頼する

導入後は、**管理したいプロジェクトのディレクトリで新しいCodexセッションを開始**します。
インストーラーを置いたリポジトリが管理対象とは限りません。
以下の例はCodexの会話欄へ入力します。

```text
このプロジェクトの進捗を確認して。残タスクと詰まっている作業を整理し、
今週の優先順位を提案して。まず調査と提案だけ。
```

```text
この不具合をIssueにして。初めて読む人にも目的と完了条件が分かる文章にして。
```

```text
この変更のPRを作って。変わる動作、確認結果、関連Issueと残作業が追えるようにして。
```

「このPRをレビューして」「Actionsの失敗を調べて」も対象です。
会話やリポジトリからGitHubが対象と分かれば、スキル名や「GitHub」という言葉を含めなくても適用します。
英語の check progress / organize remaining tasks / prioritize this week / what's blocked も同様です。
GitHubのURL、会話中のIssue・PR、リポジトリの接続先が対象の手掛かりになります。
GitHubを参考文献として挙げただけの質問や、GitHub操作を伴わないローカル作業には適用しません。

明示して使いたい場合は、依頼の前に`$github-project-director`を付けます。
これはターミナルのコマンドではありません。各プロジェクトのAGENTSを編集する必要もありません。
自動適用されない場合は、明示指定を試し、[導入確認](installation.md#導入確認)で共通ルールの状態を確認してください。

## ログインや管理対象が不足しているとき

Codexは会話・リポジトリ・利用可能な接続を先に確認し、不足が見つかった部分だけ支援を提案します。

| 状況 | 提案・質問の例 |
|---|---|
| 対象のホストへ未ログイン | 「GitHubへのログインが確認できません。こちらでログイン操作を開始してよいですか？ ブラウザーでの認証はお願いします。」 |
| `gh`がなく、ほかに使えるGitHub接続もない | 「GitHubを操作できる接続が見つかりません。こちらでGitHub CLIの導入と接続確認を進めてよいですか？」 |
| 接続済みで管理対象だけ不明 | 「管理したいリポジトリのURLかOWNER/REPOを教えてください。」 |
| 実行環境の制限で代行できない | 利用者のPCなど、操作する場所と具体的なコマンドを案内する |

認証済みのGitHub MCPが使える場合は、`gh`の導入を求めずにそれを利用します。
既知の対象や許可済みの準備は聞き直しません。Issue操作だけならProjectのボード選択も求めません。
パスワードやトークンを会話に貼る必要はなく、本人の認証操作が必要な箇所を案内します。

準備ができたら、対象へアクセスできることを読み取りで確かめ、元の依頼を続けます。
**接続準備の許可は、Issue投稿などの許可にはなりません。** 準備の経過をIssueへ記録することもありません。
これは依頼中の案内であり、インストール時の自動ログインや専用の初期設定機能ではありません。

## 調査からGitHubへの反映まで

1. 対象を特定し、本文・差分・コード・テストなど、今回の依頼に必要な根拠を確認します。
2. 調査結果や変更案を、確認できた範囲・未確定事項とともに会話へ返します。
3. GitHubへの反映が依頼・承認された範囲で変更し、再取得して結果とURLを確認します。

進捗確認や調査だけの依頼に、書き込みを付け足しません。
具体的な対象・内容の反映が既に承認されていれば、同じ承認を繰り返し求めません。
未確定の担当・期限や変更範囲は、反映前に確認します。
提案時から対象の状態が変わっていれば差分を示し、部分的に失敗した場合は成功分と未反映分を分けて報告します。

## Issueへ記録するタイミング

コメントの提案前に、共有する価値、既存記録との重複、依頼範囲を確認します。

| 状況 | 既定の対応 |
|---|---|
| 調査開始・途中経過・再試行・個々のテスト成功 | 必要に応じて会話で報告し、Issueには投稿しない |
| 状態・担当などの更新 | 承認されたフィールドを更新し、説明コメントを重ねない |
| 人の判断が必要な障害 | 影響と必要な判断をまとめる。投稿未承認なら会話で知らせ、文案を示す |
| 合意した方針・範囲の変更 | 変更と理由を記録する。本文更新で伝われば、同文コメントを省く |
| 完了・引き渡し | 成果・確認結果・残件をまとめる。関連PRで十分分かるなら追加投稿を省く |
| 定例 | 明示依頼または合意済み運用がある場合だけ、重要な変化を集約する |

通常は一区切りにまとめますが、新たな判断が必要な障害は区切りを待ちません。
変化がない場合や既に十分記録されている場合は、下書きや投稿承認の確認も増やしません。
明示的な「変化なしの報告を残して」という依頼は、その範囲で扱います。
親Issue・個別Issue・定例への同文転載や、記録先が未設定という理由だけでの定例Issue作成提案を避けます。

## 読みやすいIssue・PRにする

Issueでは「なぜ必要か・何をするか・何で完了か」、PRでは「目的・変わる動作・確認結果」を先に伝えます。
専門用語は必要なものに絞り、初出で説明します。関連リンクには「先に必要な作業」などの関係を添えます。
短い報告に見出し一式を強制せず、既存のテンプレートや言語指定を尊重します。
長い仕様を関連資料へ寄せても、目的・完了条件・重要な制約は本文に残します。

たとえば「auth hookのraceを解消」より、次のように確認できる動作から説明します。

> 再読み込み時にログイン画面へ戻る問題を修正します。
> 保存されたログイン情報の読み込みが終わってから、画面を切り替えます。

文例から未合意の実装方式・担当・予定を補いません。確認済みの結果と、これから行う作業も区別します。

## 用途別の依頼例

### 要件からタスクを作る

```text
事業目的・ユーザーストーリー・要件と既存Issueを確認し、重複しないタスク案を作って。
各案に目的、作業範囲、完了条件、根拠を付けて。まず提案だけ。
```

要件と実装・既存Issueの対応を確認し、成果を検証できる単位で提案します。
ファイルごとの機械的な分割や、すべての作業への親Issue作成は前提にしません。
技術的な保守作業に架空のユーザーストーリーを付けることもありません。
既存のSpecKit文書があれば、要件の根拠として参照できます。

### 担当・期限・優先度を計画する

```text
今後2週間の作業案を作って。既存Projectと依存関係を確認し、
優先順・担当候補・期限案・未確認の稼働条件を整理して。反映前に変更案を見せて。
```

日付・タイムゾーン・稼働条件を確認し、Projectの既存フィールドを使います。
Issueの親子関係と、着手の前提となる依存関係は区別します。
個別Issueの期限はProjectの日付フィールドで扱い、マイルストーンの期限で代用しません。

### 合意した定例Issueへ記録する

`#42`は例です。実際の記録先Issue番号またはURLへ置き換えてください。

```text
定例Issue #42へ今回の進捗を追記したい。前回からの重要な変化を、
成果・決定事項・次の行動が分かる短いコメント案にして。担当や期限は変更せず、案を先に見せて。
```

過去の本文・コメントは保持し、記録だけの依頼で担当や状態を変更しません。
投稿前に過去コメントと再試行の目印を確認し、通信失敗時の重複を避けます。
この確認は同時投稿まで防ぐ仕組みではありません。

## 結果の保存先と利用範囲

調査結果・案・反映前の確認はCodexの会話に返します。
承認後のタスクや計画はGitHub Issues／Projectsへ、定例報告は指定したIssueのコメントへ反映します。
ローカル保存も必要なら、保存先と対象を依頼に含めてください。
別の台帳DB、定期実行ジョブ、毎回のスナップショットは自動作成しません。

本番デプロイ、PRのマージ、Issueの削除・転送、管理権限の変更はこのSkillの対象外です。
接続できない場合は必要な支援を提案し、準備できなければ根拠不足を示してローカル資料で暫定分析します。
リモートの状態や反映成功を推測しません。
検証済みの範囲と限界は[記録方針と検証](behavior.md)を参照してください。

## 読み取り補助をターミナルで使う

通常はCodexが必要に応じて使います。手動実行にはPython 3.10以上と、対象へアクセスできる認証済みの`gh`が必要です。
以下は既定の導入先の例です。`OWNER/REPO`、`OWNER`、Project番号、Issue番号を実際の値へ置き換えます。

```bash
python3 ~/.agents/skills/github-project-director/scripts/github_inspect.py snapshot --repo OWNER/REPO
python3 ~/.agents/skills/github-project-director/scripts/github_inspect.py project --owner OWNER --owner-type user --number 1
python3 ~/.agents/skills/github-project-director/scripts/github_inspect.py relations --repo OWNER/REPO --issue 42
python3 ~/.agents/skills/github-project-director/scripts/github_inspect.py meeting --repo OWNER/REPO --issue 42
```

組織のProjectは`--owner-type organization`にします。
`--hostname HOST --max-pages N`はサブコマンドより前に置きます。
定例コメントの再試行確認には`meeting --entry-key KEY`を使えます。

結果は標準出力だけに返し、ファイル保存やGitHubへの書き込みはしません。
一覧の`complete`（取得完了）、`pages`（取得ページ数）、`error`（エラー）を確認し、
途中までの取得や権限不足を「該当なし」と扱わないでください。
`snapshot`のProjectはリポジトリにリンクされたものです。必要なProjectは個別に指定して確認します。
