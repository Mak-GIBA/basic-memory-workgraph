# SpecKit Upstream

[docs一覧](../README.md) · [導入手順](installation.md) · [使い方](usage.md) · [既存要件・設計の見直し](reassessment.md)

実装前に、利用者の目的・懸念・ユースケースから要件を整理し、方式研究を根拠に全体設計と検証計画を作る環境です。
このガイドは[install_speckit_upstream.sh](../../install_speckit_upstream.sh)のWorkbench 2.0.5を対象にしています。
配布スクリプトは更新資材を内蔵し、固定版ベースを取得・照合して新版を組み立てます。

## まず読む資料

新規プロジェクトの上流資料は要件・設計・検証の3文書です。研究を実行した場合はテーマ別に1本の報告へまとめます。
各文書は結論・確認してほしいこと・未確認を先に置き、必要な詳細を後に続けます。

| 確認したいこと | 正本 | 主な内容 |
|---|---|---|
| 何を作る・維持するか | `docs/upstream/requirements.md` | 目的・利用者・懸念・ユースケース、機能・品質・制約、現状と期待、不明点 |
| どう実現するか | `docs/upstream/design.md` | 研究テーマとの対応、全体構成・詳細・代表処理、技術選定と変更影響 |
| どこまで確認できたか | `docs/upstream/verification.md` | 受入条件、評価方法、組合せの確認、実際の結果、未実行、証拠 |
| 研究・実測から何が分かったか | `docs/design-research/<slug>/report.md` | 結論、候補比較、提案方式の詳説、検証、限界。実行した場合のみ |

レビューのスナップショット、JSON索引、承認台帳、生ログも内部記録として残ります。
既存の旧形式はインストーラー更新だけでは変わりません。[任意の移行](usage.md#既存資料を3文書へ移行する)を使えます。
SpecKit公式の機能別`spec.md`・`plan.md`・`tasks.md`は、必要な詳細の参照先として保持します。

日本語の要件・設計・検証文書、研究・レビュー報告は、利用可能なyomiyasuで下書きを一度推敲することを推奨します。
主張、数値、ID、条件、確認結果、根拠と断定の強さを保ち、レビュー・承認前に本文を仕上げます。
未導入でも執筆を続けます。承認済み本文を変える場合は再レビューします。

## 導入するツールと役割

| ツール・資材 | 提供元 | 役割 |
|---|---|---|
| SpecKit CLI（`specify`） | GitHubのSpec Kit | プロジェクト初期化、テンプレート、エージェント統合 |
| SpecKit Upstream Workbench（`speckit-workbench`） | このスクリプト独自 | 上流文書の雛形、対応表、構造検査、レビューと承認記録 |
| 8つの`upstream-*` Skill | このスクリプト独自 | 新規・既存・変更・不具合・改善など、目的に応じたCodexの作業手順 |
| `speckit-workbench` Skill | このスクリプト独自 | 共通入口と前版の呼び出し方との互換性 |
| Design Research | [別のインストーラー](../design-research/installation.md) | コアロジックの問い、方式比較、PoC、テーマ別の根拠・報告 |

Spec Kitは仕様を計画や実装タスクにつなげるためのツールキットです。[Spec Kit公式リポジトリ](https://github.com/github/spec-kit)
Workbenchは、目的や要求から設計・検証計画までを関連付けて管理する手順を追加します。
この追加キットはSpecKit・OpenAI・ECCの公式配布物ではありません。
文書の構成や追跡方法は独自の運用で、規格への完全準拠を保証するものでもありません。

## どのような場面で使うか

- 新しいアプリについて、利用者の目的と懸念から、何を作るかを決めたい。
- 既存アプリの現状と、合意済み仕様・今後の変更案を分けたい。
- 要件変更が設計や検証計画のどこに影響するか追いたい。
- 検索・抽出などの方式を研究し、複数の結果を全体設計へ統合したい。
- 承認した文書が後から変わっていないか確認したい。

Codexで対象プロジェクトを開き、短く目的を伝えます。

```text
$upstream-new 社内文書を検索し、根拠を確認して回答できるアプリを作りたい。
```

```text
$upstream-change 検索の取りこぼしを減らしたい。速度と費用の制約も含めて見直して。
```

ストーリー → 懸念 → ユースケース → 要件 → コアロジックの問い → テーマ別研究 → 統合設計 → 検証計画の順で進めます。
新規設計や実現方式を変えるTo-Be設計では、該当テーマの研究を実行してから設計を確定します。
標準的な実装は根拠付きの`standard`分類で扱い、As-Isの整理や誤字修正に全体の再研究を一律に要求しません。
Design Researchが使えない場合は要件・As-Isを整理し、必要な研究を未実行として設計確定を止めます。
画面例を含める場合は、利用可能なUI/UX Skillを実際に適用します。

8つのSkill、図の読み方、画面例、レビュー・明示承認は[使い方](usage.md)にまとめています。
研究テーマの分割・統合と既存判断の見直しは[ユースケース別ガイド](reassessment.md)を参照してください。
研究完了は採用承認ではなく、実装開始も別の依頼です。

## 導入は2段階

1. ユーザー共通環境へCLI・資材・Skillを配置します。
2. `attach`で対象アプリに文書雛形と設定を追加します。

公式の`specify` CLIが見つからない場合は、`specify-cli==1.0.8`を専用venvへ取得します。
既存CLIは互換性を確認して再利用し、自動更新しません。
UpstreamとDesign Researchは別途導入します。組み立て工程で両スクリプトを作ることと、両方を導入することは別です。
2026-10-10に組み立ての停止原因を修正し、両ツールの組み立て・自己テストと、このPCでの更新・診断を確認しました。
[導入手順](installation.md)と[現在の検証範囲](../design-research/validation.md)を参照してください。

## 検査できることの範囲

`check`や`gate`は文書の構造、参照、必要項目、研究と設計の対応、承認情報などを検査します。
新規・変更設計はv2で要件・研究計画・テーマ別run・統合状態を対応させ、旧v1は互換性のため読み取ります。
要件の意味的な十分性、出典やテスト結果の真偽、承認者の本人認証までは判定しません。
SkillはCodexへの指示であり、アクセス制御や全操作の強制停止機構ではありません。
アプリのテストやCI必須チェックは自動設定されません。

## 詳細資料の確認方法

導入後の`releases/2.0.5/README_COMMANDS.md`と`assets/references/`に操作ガイドと参照資料が配置されます。
研究連携は`RESEARCH_FIRST.md`・`RESEARCH_WORKSTREAMS.md`にまとまっています。
`--extract-bundle`は通信せず更新元を展開し、`--extract`は組み立て後の資材を展開します。
保存先・組み立てと展開の条件は[導入手順](installation.md)、作業で作る文書は[成果物一覧](reassessment.md#成果物の保存先と確認先)を参照してください。

このガイドは同梱の更新資材と固定版の実装を基準にしています。
外部Spec Kitの一般説明は2026-09-29に確認した内容です。最新版の操作を固定版へそのまま適用する前提ではありません。
