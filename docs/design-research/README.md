# Design Research

[docs一覧](../README.md) · [導入手順](installation.md) · [使い方](usage.md) · [検証結果](validation.md)

プロジェクトの中心的な目的に貢献するコアロジックを、方式の比較・実測を通じて改善するCodex用キットです。
検索・抽出・分類・推論・業務処理などを支える技術、アルゴリズム、AIエージェントを対象にします。
関連するAPI・データ保存・認証・ジョブなどのバックエンドも含め、依頼された範囲で修正と再検証を行えます。

入口は[install_design_research.sh](../../install_design_research.sh)です。
2.0.1は、調査・比較・検証・実際の修正結果を`docs/design-research/<slug>/report.md`の1報告書にまとめます。
冒頭に結論・判断待ち・未確認・実行状態を置き、対象に必要な節だけ続けます。生ログ・JSON・証拠・実行ごとの保存版は内部に残します。
Skillと実行コードを内蔵した単一ファイルなので、このスクリプトだけで導入できます。
既存の旧形式は更新後も保持し、[任意の移行](usage.md#既存資料を1報告書へ移行する)で統合できます。

日本語の調査・レビュー・検証レポートは、下書きを利用可能なyomiyasuで一度推敲することを推奨します。
主張、数値、ID、条件、確認結果、根拠と断定の強さを保ち、未導入でも執筆と文書確認を続けます。
子ロールにも同じ方針を渡し、生成に使う説明欄を整えてから構造化結果を返します。

## 目的に合わせた3つの使い方

| やりたいこと | モード | 実際に行うこと |
|---|---|---|
| コアロジックの方式・評価方法を比較したい | `research` | 現行方式や単純な基準案と候補を比較し、複数文献と実測の根拠を確認。必要なローカル実験を別の作業場所で実行 |
| コアロジックや関連バックエンドの問題を知りたい | `audit` | 関連する検証を実行し、再現手順・結果・改善案を報告。アプリのコードは保持 |
| 依頼したロジックを改善・修正したい | `run` | 目的への貢献と制約を確認して修正・検証し、別の評価実行で結果を確認 |

アプリ以外の研究・比較・評価・検証も対象です。APIやデータベースがあることを前提にしません。
仕様書がなくても、相談内容・既存コード・利用条件から始められます。
方式・精度改善の調査では、原則として独立した一次文献を2件以上読み、方法・評価条件・結果・限界を比較します。[文献の読み方](usage.md#複数の文献を深く比較する)

SpecKit Upstreamと組み合わせる場合は、既存要件・評価方法・精度改善の研究結果を、要件・設計判断・検証計画へ戻せます。
Workbench 2.0.1のSkillには、必要な場面でDesign Researchの利用を明示して実行する手順があります。
利用条件と入力例は[既存要件・設計の見直し](../speckit-upstream/reassessment.md)にまとめています。

## Codex画面から使う

導入後、対象プロジェクトをCodexで開き、会話欄に次を入力します。
`/path/to/project`は実際の対象へ置き換えてください。

```text
$design-research
/path/to/project の検索方式を、現行方式を含めて比較して。
主要な目的と改善する指標を確認し、複数の一次文献の方法・評価・限界を深く読んで判断して。
導入済みの scripts/gan-harness.sh をBashで実際に実行して。
必要な小さなPoCも実行し、結果と根拠へのリンクを残して。
新しい依存や運用手順を増やす前に、もっと単純な案で足りるか確認して。
```

Skillと表示設定の両方に、導入済みのBashを実行する指示を含めています。
手動コマンド、コアロジックの改善やバックエンド修正の依頼例、再開方法は[使い方](usage.md)にあります。
実行できない場合は、実行したように扱わず、診断結果と不足する条件を報告します。

## UI/UXキットとの関係

画面を使う際の迷い・見た目・操作導線は[UX Stack](../codex-ux-stack/README.md)、
その裏側の処理・保存・権限・再試行や方式の妥当性はDesign Researchで確認できます。
それぞれ単独で導入・実行できます。
既存のUI/UXレビューは任意の入力として渡せますが、必須ではありません。
画面のスクリーンショットだけから、見えていないサーバー構成を推測して決めません。

## 指摘を増やすより、解決を優先する

最初に決めた確認基準を保持し、修正は1回につき最大3つの原因に絞ります。
初回評価を含む最大5回で止まり、2回続けて改善しない場合も止まります。
追加する依存・サービス・設定には、単純な案より良い理由を求めます。

修正担当の「直した」という申告だけでは完了にしません。
親スクリプトが実行した検証と、その変更後の別レビューを確認します。
根拠不足・通信失敗・実行不能・未確認は、その状態のまま報告します。

## 収録内容と前提

| 資材 | 役割 |
|---|---|
| `SKILL.md`・`agents/openai.yaml` | Codexからの入口と、実Bashの実行指示 |
| `scripts/gan-harness.sh` | 調査・検証・修正・再開・診断のBash入口 |
| `scripts/harness.py`・`runtime.py`・`evidence.py`・`report.py` | 反復制御、隔離した実行、根拠の検査、Markdown出力 |
| `scripts/research.py`・`literature.py`・`dossier.py` | 既存の文献調査CLIと証拠台帳の検証 |
| `references/`・`templates/` | 調査手順、実行・復旧方法、根拠形式、報告の雛形 |

導入と補助CLIはBash・Python 3.10以上で動きます。
ハーネスには、認証済みのCodex CLIと動作するコマンド用サンドボックスが必要です。
導入自体は通信せず、MCPや個人のCodex設定を変更しません。

文献検索はarXiv・Semantic Scholar・Crossrefの書誌情報・要旨・リンクを取得します。
論文の該当箇所の読解には、既存のブラウザー・PDFツールや提供資料を使います。
外部資料の取得成功は、その主張の正しさや全文読解の証明ではありません。

導入済みの[Basic Memory Workgraph](../basic-memory-workgraph/README.md)には、後の判断・再現・再開に有用な検証・実験の詳細を選んで保存できます。
明示依頼がなくても保存でき、案件固有の成功・失敗も対象です。保存時は既存の設定・書き込み許可に従います。
[保存内容・場所・確認方法](usage.md#検証実験の詳細をworkgraphへ残す)を参照してください。

成果物は対象の `docs/design-research/<slug>/` に保存します。
指摘から実行結果・標準出力・生成ファイルへたどれるリンクを作り、修正前後も残します。
何を確認するときにどのファイルを読むかは、[成果物一覧](usage.md#根拠と成果物)で確認できます。
画像は、実際の検証で保存したものがある場合に紐付けます。
検証範囲と実機上の制約は[検証結果](validation.md)を参照してください。
