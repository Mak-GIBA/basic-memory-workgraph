# Design Research

[docs一覧](../README.md) · [導入手順](installation.md) · [使い方](usage.md) · [検証結果](validation.md)

検索・抽出・分類・推論など、プロジェクトの目的を支えるコアロジックの方式を比較し、根拠と検証結果から改善案をまとめるCodex用キットです。
このガイドは[install_design_research.sh](../../install_design_research.sh)の2.4.0を対象にしています。

効果・精度・性能の検証では、実験前に主要指標、採点、比較条件、採用条件を固定します。
報告には同じ入力に対する基準案・候補案の最終出力と採点を載せ、実行記録から数値を再計算します。
主要効果が未測定なら効果検証は未完了です。設計・文献調査は、効果未測定を明示した条件付きの結論で完了できます。
比較設計と実験コードを別工程として保存し、同条件の再開では完成済みの工程を再利用します。

## 目的から入口を選ぶ

研究の入口は`$design-research`です。対象プロジェクトをCodexで開き、知りたいことを短く入力します。

```text
$design-research 検索精度を改善して
```

```text
$design-research 前回の研究結果を踏まえて、別の方式も検討して
```

```text
$design-research 研究はどこまで進んだ？残りの検証も教えて
```

Skillは要件・現行実装・研究計画・過去の実行を確認し、目的に合う工程を選びます。
テーマ数、比較手法数、図の種類、CLIのフラグを毎回指定する必要はありません。
「計画だけ」という依頼は計画で止まり、進捗確認では実験を開始しません。
対象や過去結果が複数あり、判断に必要な場合は確認します。

| やりたいこと | 入口 | 最初に確認する成果物 |
|---|---|---|
| 特定の技術・アルゴリズムを研究する | `$design-research` | テーマ別の`report.md` |
| 必要な研究テーマを整理する | `$design-research`に「計画だけ」と添える | 研究計画と依存関係 |
| 完了した研究を新しい条件で見直す | `$design-research` | 新しい実行の報告と前回との差 |
| システム全体の要件と設計を作る・変える | `$upstream-new`／`$upstream-change` | 要件・設計・検証計画 |

`$...`はCodexの入力欄で選択するSkill名です。ターミナルのコマンドとは用途が異なります。
自然文からの暗黙のSkill選択はCodexの挙動に依存するため、入口を指定する場合は`$design-research`を明示します。

## 研究で確認すること

方式の比較では、現行の基準法と原理の異なる候補を含む約5手法を目安にします。
これは研究テーマごとの候補数です。テーマ数を5に固定したり、意味のない候補で数を埋めたりしません。
重要な一次文献は方法・評価条件・結果・限界まで読み、実行可能な小規模実験で比較や反証を行います。
文献の報告値、前回の測定、今回の実測、仮説、未測定を分けて記載します。

人が読む資料は通常`docs/design-research/<slug>/report.md`です。
目的と具体例、用語、図の読み方から説明し、提案手法がある場合は独立した章で構成・入出力・数式や擬似コード・既存法との差・負担と限界を示します。
生ログ・JSON・実行ごとの保存版も保持します。[成果物の読み方](usage.md#根拠と成果物)

日本語の報告は、利用可能なyomiyasuで下書きを一度推敲することを推奨します。
主張、数値、ID、条件、根拠、断定の強さを保ち、未導入でも執筆と内容確認を続けます。

## Upstreamとの役割分担

[SpecKit Upstream](../speckit-upstream/README.md)はストーリー・ユースケース・要件・全体設計・検証計画を担当し、Design Researchは技術的な問いの比較と根拠を担当します。
新規設計や実現方式を変える設計では、必要なコアロジックを研究テーマに分け、研究結果を統合してから設計を確定します。
標準的な実装は既存の根拠で説明し、単純なAs-Isの整理や誤字修正に比較研究を一律に要求しません。

各テーマの研究を個別の報告へまとめます。Upstreamが接続条件と全体の品質・応答時間・資源量を確認し、`design.md`へ反映します。
研究計画に独立したテーマがあっても、同じプロジェクトの実行はロックにより直列です。自動並列起動・結果回収は行いません。
具体例は[使い方](usage.md)、全体設計への戻し方は[既存要件・設計の見直し](../speckit-upstream/reassessment.md)を参照してください。

## 監査・修正とUI/UX

従来の`audit`はコアロジックや関連バックエンドの検証、`run`は依頼されたコード修正と再検証を扱います。
修正では影響の大きい最大3つの原因に絞り、変更後の別レビューで根拠を確認します。
研究・設計の依頼から修正へ進む権限は自動で追加されません。手動の操作例は[使い方](usage.md#ターミナルから直接実行する)に残しています。

画面の対象・操作・状態・導線は[UX Stack](../codex-ux-stack/README.md)の担当です。
画面例を含むUpstream設計では利用可能なUI/UX Skillを適用し、静止画・プロトタイプ・実アプリの確認範囲を分けます。
Design Researchへ既存のUI/UXレビューを任意で渡すこともできます。スクリーンショットだけからサーバー構成を推測して決めません。

## 導入と確認

BashとPython 3.11以上を使います。配布スクリプトは固定版ベースを取得・照合してから新版を組み立てるため、通常の導入には通信が必要です。
ネットワークを使わず組み立てる場合は、指定された固定版の元スクリプト2本を用意します。[導入・オフライン利用](installation.md)
研究ハーネスには、認証済みCodex CLIと動作するコマンド用サンドボックス、対象に必要な検証環境が必要です。

旧ショートカットSkillは現在の推奨入口には含めません。更新時は未編集の管理対象だけを退避し、ユーザー編集済み・管理外の同名フォルダーを保持します。
既存の旧形式の研究資料も保持し、[任意の移行](usage.md#既存資料を1報告書へ移行する)で統合できます。

導入済みの[Basic Memory Workgraph](../basic-memory-workgraph/README.md)には、後の判断・比較・再現に有用な検証・実験の記録を、既存の設定と書き込み許可に従って保存できます。[保存内容と確認方法](usage.md#検証実験の詳細をworkgraphへ残す)
研究の完了、方式の採用承認、システム全体の性能確認は、それぞれ結果と根拠を確認します。
2026-10-10に組み立ての停止原因を修正し、両ツールの組み立て・自己テストと、このPCでの更新・診断を確認しました。
各試験の範囲と実モデルでの未確認事項は[検証結果](validation.md)にまとめています。
