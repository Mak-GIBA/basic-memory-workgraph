## 調査の中心はコアロジックの改善

Design Research 2.4.0の入口は`$design-research`に統一されています。
対象プロジェクトをCodexで開き、目的を短く伝えます。モード名・候補数・図・CLI引数を依頼文に列挙する必要はありません。

```text
$design-research このプロジェクトの検索精度を改善する方法を調べて。
```

Skillは、主要な目的、改善する指標、維持する制約、現行方式と過去の研究を確認します。
検索・ランキング、抽出、分類、推論、判断ルール、業務処理などのうち、成果を左右する問いを研究対象にします。
対象が単一の方式か、複数のコアロジックに分かれるかを判断し、今回の範囲と次の作業を示して進めます。
対象プロジェクトや過去研究を一意に選べない場合は、必要な点だけ確認します。

## 複数の文献を深く比較する

方式比較では、1テーマにつき現行方式などの基準案に、原理の異なる候補約4案を加えた約5案が目安です。
これは研究テーマの数ではありません。適用できない案を数合わせで増やさず、候補を減らした場合は理由を残します。
汎用的な比較を行う`comparison`が既定です。提案方式の詳細設計が必要なら`proposed-method`を選びます。

効果検証では、主要指標が目的に対応しているかを実験前に確認し、採点・入力・統制条件・採用条件を固定します。
例えば推論補助なら、同じモデルと予算で実際の課題を解かせ、最終回答を採点します。
ツールが応答したこと、思考文を受け付けたこと、返却文字数だけでは推論精度を測ったことになりません。
検索・コード生成・処理時間の評価も、最終成果の正しさと測定範囲を目的に合わせます。

同じ入力に対する期待値と基準案・候補案の実出力を保存し、ハーネスが採点を再計算して報告へ載せます。
異なる課題数と繰り返し試行数を区別し、失敗例と適用限界を残します。改善なし・同等も有効な測定結果です。
主要効果の未測定は効果検証を未完了にします。設計・文献調査だけの依頼では、未測定と明示して条件付きで完了できます。

内部CLIの`--evaluation-purpose`はauto / effectiveness / design / literatureです。
Skillが依頼から選び、prepareのdispatch hashと研究計画で固定します。目的を変えた再開はできません。
新規runでは比較設計と実験コードの作成を別々に保存します。中断時は既存の実行記録と保存済み工程を確認して再開します。
モデル処理の時間切れと検証の失敗はrole receiptで区別できます。書式・引用範囲・課題履歴の補正は、元の時間予算内で一度だけです。

方式・精度改善の調査では、原則として独立した一次文献を2件以上読みます。
論文は方法・実験・考察の該当箇所まで確認し、次を比較します。

| 比較する内容 | 確認する点 |
|---|---|
| 方法・仕組み | どの前提で、何を改善する方式か |
| 評価条件 | データ・タスク・モデル・版・指標・資源条件 |
| 比較対象と結果 | 基準案・対照実験との差と、測定された範囲 |
| 限界と相反する知見 | 失敗条件、対象外、他の文献と異なる結果と条件 |
| 対象プロジェクトへの適用 | 目的・入力・制約との適合、必要な追加実測 |

同じ研究のプレプリント・出版版や転載は、独立した複数の根拠として数えません。
要旨や検索結果を見ただけ、あるいは資料を取得しただけでは、深く読んだとは扱いません。
判断を支えるページ・節・図表、読めなかった箇所、予算内で確認できない点を記録し、根拠が不足する判断は保留します。
文献数だけを数える完了条件は追加せず、既存の実行予算を使います。
原因と対策が明らかな小さな不具合には、文献調査を一律に要求しません。

## Codexで目的を伝える

次の例はCodexの会話欄への入力です。`/path/to/project`は実際の対象へ置き換えます。

| やりたいこと | 入力例 | 今回の作業 |
|---|---|---|
| 一つの方式を比較する | `$design-research /path/to/project の文書抽出方式を比較して。` | 方式比較、必要な小さなPoC、報告 |
| 研究テーマだけを分ける | `$design-research この要件を研究テーマに分けて。今は計画だけ。` | 要件と研究テーマの対応、依存・実行順。実験は始めない |
| 複数テーマを研究する | `$design-research 検索の候補生成と順位付けを分けて調べ、組合せの条件も整理して。` | テーマ別研究と統合先への引き渡し |
| 完了した研究を再評価する | `$design-research 前回の検索研究を、新しいデータ条件で見直して。` | 過去研究を参照した別の研究 |
| 中断した研究を続ける | `$design-research 中断した研究を、同じ条件で続けて。` | 対象runを照合して再開 |
| 今の状況だけを確認する | `$design-research 今の研究結果と、残っている作業を教えて。` | 記録・報告の読み取り。実験は始めない |

内部では`plan`・`research`・`workstream`・`reassess`・`resume`・状況確認を使い分けます。
これらは別々のユーザー向けSkillではありません。
2.3.0の`$design-research-plan`などのショートカットは、2.3.1では管理対象の未編集版だけ退役します。
更新と独自編集の扱いは[導入手順](installation.md#既存版からの更新)を参照してください。

監査や修正も、同じ入口で目的と範囲を伝えます。

```text
$design-research APIと保存処理を、不正入力・二重送信・失敗後の復旧で検証して。
本番データは使わず、コードは変更しないで。
```

```text
$design-research このプロジェクトで保存が重複する問題を直して。
既存の変更を守り、修正前後の検証と別レビューを報告して。
```

監査には`audit`、明示されたローカル修正には`run`を使います。
研究や状況確認だけの依頼から、アプリ修正へ進むことはありません。
実行コマンド、実行ID、実際の状態と報告で、導入済みハーネスが起動したことを確認します。
Skillは自身の配置先を使うため、新規の`.agents/skills`と既存の旧配置のどちらでも呼び出せます。
実行できない場合は、前提不足と停止理由を残します。

## SpecKitの要件・設計見直しと組み合わせる

機能やシステム全体を整理したい場合は、`$upstream-new`または`$upstream-change`から始めます。
SpecKit Upstream Workbench 2.0.5がストーリー・懸念・ユースケース・要件と全体設計を担当し、
Design Researchが方式を左右するコアロジックの問い、候補比較、PoCと研究報告を担当します。
各キットは別途導入します。Design Researchだけを使う場合、SpecKitの導入や文書は必須ではありません。

```text
$upstream-new 社内文書を検索し、根拠を確認して回答できるアプリを作りたい。
```

新規設計や実現方式を変えるTo-Be設計では、該当テーマの研究を実行してから設計を確定します。
標準的なCRUDなどは研究計画で`standard`に分類し、既存の根拠を示します。
As-Isの整理や誤字修正に全体の再研究を一律に要求するものではありません。

複数の問いがある場合は、要件を研究テーマに分け、テーマごとの入力・出力、評価条件、依存、予算、統合条件を固定します。
たとえば候補生成・順位付け・組合せ検証は、各テーマの報告を全体設計へ戻します。
計画上で同時に進められるテーマがあっても、現在の同一プロジェクトの実行はロックで直列化されます。
依存順の計画を表示しただけで、実験が自動起動したり並列実行されたりするわけではありません。
[テーマ分割と統合の例](../speckit-upstream/reassessment.md#複数のコアロジックを研究テーマに分ける)も参照してください。

引き渡す内容は、関連要件ID、採用候補と代替案、入力・出力契約、実測と不足する根拠、費用・制約、
実行ID、保存版の報告へのリンク、`design.md`への反映案です。
Upstreamが組合せと全体のトレードオフを確認し、要件・設計・検証計画へ反映します。
研究完了は採用承認ではありません。レビュー、明示承認、アプリ実装はそれぞれ別の段階です。
[場面別の入口](../speckit-upstream/reassessment.md)で、要件見直し・精度改善・不具合・条件変更の使い分けを確認できます。

## ターミナルから直接実行する

新規のユーザー共通導入では次のパスです。
プロジェクト導入・旧配置・独自配置では、インストーラーが表示した実際のパスへ置き換えます。

```bash
DR_GAN="$HOME/.agents/skills/design-research/scripts/gan-harness.sh"
bash "$DR_GAN" doctor --project /path/to/project
bash "$DR_GAN" research --project /path/to/project --slug search-options \
  --brief "現行方式と候補を正しさ・応答時間・運用負荷で比較し、必要なローカル実験を行う" \
  --reader-friendly --report-profile proposed-method --target-methods 5 \
  --allow-network
```

`--allow-network` を付けた場合、学術API・公開資料の取得とCodexのライブWeb調査を許可します。
付けない場合、これらは無効です。`--offline` でも明示できます。
これはこのキットの調査通信の指定であり、モデルへの接続や既存MCP全体の通信遮断ではありません。
私有コードや機密条件をそのまま外部検索語にしない手順を含めています。

レビューと修正の例です。
`python3 -m pytest tests/test_api.py` は例なので、対象に存在する安全な検証コマンドへ置き換えてください。
必要なアプリ依存は事前に用意します。ハーネスは依存を自動導入しません。

```bash
bash "$DR_GAN" audit --project /path/to/project --slug api-review \
  --brief "不正入力と二重送信で保存結果が正しいか確認する" \
  --test-command "python3 -m pytest tests/test_api.py"

bash "$DR_GAN" run --project /path/to/project --slug api-fix \
  --brief "不正入力と二重保存の問題を最小の変更で直す" \
  --test-command "python3 -m pytest tests/test_api.py"
```

`--test-command` は複数指定でき、研究モードでも必須の実行対象になります。
終了コードだけでなく、レスポンス・保存状態・権限・再試行後の状態を確認する検証を選びます。
対象にない機能のチェックは追加しません。

## ローカルサービス・テスト用データ

検証コマンドは、実際のプロジェクトをコピーした一時作業場所で実行します。
研究のPoCも一時作業場所に生成します。どちらも実行結果を保存してから一時領域を片付けます。
通常の検証では、個人のHOME・環境変数やプロジェクトの `.env` を自動で引き継ぎません。
既存の `node_modules`・`.venv` は、サンドボックス内で読み取り用リンクとして再利用できる場合があります。

検証用サービスの起動が必要なら、次を追加できます。

```bash
bash "$DR_GAN" audit --project /path/to/project --slug service-review \
  --brief "検証用APIの入力・保存・復旧を確認する" \
  --start-command "python3 test_server.py" \
  --url "http://127.0.0.1:8099/health" \
  --test-command "python3 check_api.py" \
  --test-env-file /path/to/private/test.env
```

これも例です。対象に存在する起動・検証コマンドと、空いているポートを選びます。
`--url` は資格情報を含まないローカルのループバックURLに限定します。
すでに応答するURLに `--start-command` で接続すると停止します。
スクリプトが起動したプロセスだけを終了し、他のサービスは終了しません。
検証コマンドには `DR_GAN_TEST_URL` で指定URLを渡します。

`--test-env-file` は `KEY=VALUE` 形式の明示した設定だけを読みます。
シェルとして実行せず、変数展開もしません。本番モードの指定やシステム用の環境変数は拒否します。
ただし、任意の接続先がテスト用DBかどうかまでは判定できません。
専用のテストDB・ダミーデータを使い、検証が初期状態を用意できることを確認してください。
明示した検証用サービスへの接続では、検証のサンドボックス内で通信を許可する場合があります。

## UI/UXレビュー・模範実装を任意で渡す

Design ResearchとUI/UXキットはそれぞれ独立して導入・実行できます。既存のUI/UXレビューがなくても開始できます。
ある場合は、コマンドに `--review /path/to/ui-ux-review.md` を追加します。
レビューを入力として保存し、関連するバックエンドの問題は実際に再現します。

模範になる公開実装や公式資料が分かっていれば、
`--reference-url https://example.org/actual-source` を追加できます。
例のURLは実在する参照先へ置き換え、公開資料の取得には `--allow-network` を指定します。
取得不能・未読・適用範囲外を区別し、見た目だけで内部構成を決めません。

参照先が未指定でも、調査に必要なら良い設計例を探す手順を含めています。
候補を増やすこと自体は目的にせず、取り入れる点と単純な代替案をまとめます。

## 実行の流れと終了条件

1. 別のCodex実行で、目的・基準案・確認項目・合格条件を決めます。
2. 研究では提案と必要なPoC、コアロジック・バックエンドの監査や修正では宣言した検証を実行します。
3. 別のCodex実行で、実際の根拠と失敗・復旧・複雑さを評価します。
4. `run` では影響の大きい最大3つの原因を修正し、検証と評価を繰り返します。
5. 根拠・修正前後・未確認事項・停止理由を保存します。

初回に決めた確認基準は途中で緩めません。
既定は初回評価を含む最大5回で、`--max-iterations` で1〜5回を指定できます。
2回続けて改善しない場合は `plateau` で停止します。
既定の `--phase-timeout` は1段階／検証あたり1800秒です。

必須の実行チェックには、同じ反復・同じソースで成功した記録が必要です。
同じ確認項目に失敗した検証が残っていれば、別の成功で隠せません。
修正担当の申告だけでは指摘を解消済みにせず、変更後の別レビューで根拠を確認します。

| 状態 | 意味 | 終了コード |
|---|---|---:|
| `research_complete` | 必須の研究・根拠・実行条件を満たした条件付きの提案 | 0 |
| `passed` | 必須チェック・未解消Critical/Highなし・複雑さの評価を満たす | 0 |
| `reviewed` | auditの報告が完成。指摘や検証失敗は残り得る | 0 |
| `blocked`・`cancelled` | 前提不足・根拠の不整合・失敗・中断 | 2 |
| `plateau`・`limit_reached` | 改善停滞・上限到達。完了条件は未達 | 2 |

研究の完了は、方式がすべての条件で有効だという証明や、人間による採用承認ではありません。
`run` の完了も、記録した検証範囲についての評価です。

## 根拠と成果物

新規topicの人向け資料は`docs/design-research/<slug>/report.md`の1本です。
結論を読んだ後に、方式・比較条件・根拠の順で確認できます。

| 報告の内容 | 確認できること |
|---|---|
| 結論と確認してほしいこと | 実行ID・状態、推奨、停止理由、判断待ち、未確認 |
| 問題・条件と候補比較 | 目的・制約、基準案と約5候補、出典、採否理由 |
| 提案方式の詳説 | 仕組み、全体・モジュール・既存方式との差の図、必要な式や擬似コード、成立条件と限界 |
| 調査・実験・検証 | 評価条件、実測、反証・切り分け実験、指摘と再現。行った範囲だけ |
| 変更と再検証 | `run`で行った変更と別レビューによる前後検証。変更した場合だけ |
| 残る確認と実行記録 | 未測定、未実行、再確認条件、再開方法、根拠へのリンク |

提案方式は比較表の一行で済ませず、独立した節で説明します。既存方式の選定だけなら新規性を作りません。
図には問いと読み方を添え、全体図でどの部品を拡大したか分かるようにします。
数値・条件を保ち、実測、文献の報告、推論・仮説、未測定を区別します。
図や報告が完成していても、実験を実行した証拠にはなりません。

Skillの最終回答は結論と報告へのリンクを中心に案内します。
JSONや生ログは、結果・停止理由を調べる必要がある場合だけ補足します。日本語の文章には利用可能なyomiyasuを使います。
SpecKitと併用する場合は、採用理由・適用条件を`design.md`へ、評価条件・実際の結果を`verification.md`へ戻し、報告の全文は複製しません。

機械用の状態・証拠台帳・検索記録は`.internal/status.json`・`.internal/evidence.json`・`.internal/research-log.json`です。
証拠にはID・ハッシュ・反復・対象ソースを残し、評価前と再開時に照合します。
実際のreceiptから標準出力・標準エラー・生成結果を確認できます。
`runs/<run-id>/`に状態・役割出力・PoC・生ログ・証拠を残します。同じ実行の`reports/report.md`が報告の保存版です。
仕様から長期参照する場合は、`docs/design-research/<slug>/runs/<run-id>/reports/report.md`と実行IDを使います。
実行開始前の資料は`inputs/`へ保存します。
最新の`report.md`は実行開始時と停止時にも今回の状態を表示し、前回の成功報告と取り違えないようにします。
生成するJSON・図・画像は確認計画の`artifact_paths`に宣言し、実ファイルを保存します。画像は報告にも埋め込みます。

日本語の調査・レビュー・検証レポートには、利用可能なyomiyasuで下書きを一度推敲することを推奨します。
主張、専門用語、数値、ID、条件、確認結果、根拠と断定の強さを保ちます。未導入でも執筆を続けます。
子ロールは説明欄を整えてからJSONとして返します。生成済みレポート、台帳、生ログ、過去の保存版は保持します。

## 既存資料を1報告書へ移行する

```bash
bash <skill-dir>/scripts/gan-harness.sh migrate --project . --slug TOPIC
# 統合本文・リンク変更・バックアップを確認してから適用
bash <skill-dir>/scripts/gan-harness.sh migrate --project . --slug TOPIC --apply
```

旧5種類のMarkdownをreport.mdへ、トップレベルの機械用JSONを.internal/へまとめます。
元の文書は.internal/migrations/へバックアップし、ID・出典・証拠へのリンクを保持します。過去のruns/・receipt・保存版は書き換えません。
保持する独自文書から旧資料へのリンクがある場合は、先に修正してください。実行中、壊れたJSON・証拠、統合先の競合では停止します。
適用中の失敗では元に戻し、移行済みの再実行は変更しません。移行は研究の再実行や方式の採用承認ではありません。
更新だけでは旧形式を変更しません。旧topicでは従来の保存先を使い、rootのstatus.jsonと報告の実行IDを照合してください。

## 検証・実験の詳細をWorkgraphへ残す

[Basic Memory Workgraph](../basic-memory-workgraph/README.md)が導入・設定されていれば、外側のDesign Research Skillが有用な検証・実験の詳細を選んで保存できます。
明示依頼がなくても、後の判断・比較・再現・再開に役立つ記録は保存対象です。案件固有の結果や、失敗した方法も含みます。
通常の成功ログや全実験を無条件に保存せず、選んだ検証・実験ごとに1つの詳細ノートを作ります。

| ノートに残す内容 | 詳細 |
|---|---|
| 目的と有用性 | 問い・仮説、主要な目的への貢献、後のどの判断・再現・再開に役立つか |
| 対象と条件 | 対象版、実行ID・Evidence ID・反復、入力・評価データ、環境・モデル・資源条件、基準案と制御変数 |
| 評価と再現 | 指標・期待結果・判定条件、実行したコマンド、必要な準備と再現方法 |
| 実際の結果 | 値・終了状態、成功・失敗・未確認、中断・出力上限、重要な出力やエラー、共通条件での差 |
| 解釈と根拠 | 確認できた範囲、失敗の根拠、推論・限界・再確認条件、実行記録・生の結果・保存版の報告へのリンク |

長い生ログ、データ、生成コード、論文本文は元の成果物へリンクします。未実行を実測として記録しません。
保存先は、設定済みBasic Memoryプロジェクト内の`artifacts/design-research/<slug>/<run-id>/<evidence-id>.md`です。
対象リポジトリの`docs/design-research/`とは別の場所に保存します。
同じ実行・Evidenceの記録を検索して重複を避け、保存後に読み戻します。
最終回答には実際のMemoryプロジェクト・ノート参照先、保存理由、保存状態を示します。

保存内容を指定する例です。保存を明示すると、対象と範囲を指定できます。

```text
$design-research
このプロジェクトの検索方式をresearchで比較・実測して。
比較実験ごとの条件・指標・コマンド・結果・失敗理由・再現方法を、設定済みMemory Workgraphへ詳しく保存して。
実行根拠と報告の保存版へのリンクを残し、保存したノートの参照先も示して。
```

保存時は既存の書き込み許可・保存設定に従います。Plan・読み取り専用モードや保存禁止の指定がある場合は書き込まず、`auto=off`では自動保存しません。
抽象的なRule・Workflow・Validationへ一般化する場合は、Workgraphの既存の保存基準で別途判断します。
Memoryが未導入・利用不能、検索失敗、保存失敗の場合はその状態を報告し、ローカルの研究成果物を保持します。
この保存はSkillが担当します。ターミナルからBashハーネスを直接実行しただけではMemoryに書き込みません。
インストーラーはWorkgraphの設定を変更せず、ハーネス内の子役もMemoryを書き込みません。

## 停止と再開

同じ入力・同じ条件で中断した実行を続ける場合は`resume`、完了した研究を新しい条件で見直す場合は`reassess`を使います。
Codexでは「中断した研究を続けて」「前回の研究を新しい条件で見直して」と伝えれば、Skillが記録を照合します。

### 同じ条件の中断から再開する

```bash
bash "$DR_GAN" resume ACTUAL_RUN_ID --project /path/to/project
```

`ACTUAL_RUN_ID`は`report.md`冒頭、`.internal/status.json`または実行結果のJSONにあるIDへ置き換えます。
ソース・記録のハッシュ・明示したテスト設定が変わっていれば、再開を拒否します。
評価待ちの中断は、検証を重複実行せず評価から続けます。

検証・実験の途中なら、前の記録を保持して新しい反復と一時作業場所で実行します。
検証コマンドは再実行され得るため、テストデータを安全に初期化できる必要があります。
残りの反復がなければ、新しい実行を始めます。
修正中に止まった場合は差分を保持し、再開を拒否します。差分を確認して新しい`audit`／`run`で再検証してください。
完了・停滞・上限到達の実行も、新しい作業として開始します。
ユーザーの変更をresetして再開条件に合わせることはしません。

### 完了した研究を再評価する

`reassess`には、完了した過去runの状態と保存版の報告が必要です。
過去の問い・推奨・制約と今回の変更を整理し、新しいslug・runで独立した報告を作ります。
以前の採用案を比較対象に含め、少なくとも1案は異なる原理から検討します。
旧報告・根拠は書き換えず、異なる条件の数値を直接比較しません。現行案も新しい条件で評価します。
過去runを一意に選べない場合は選択を確認し、未完了runを完了済みの再評価として扱いません。

### 状況だけを確認する

導入済みSkillのパスを使います。次のコマンドは記録を読み、実験を起動しません。

```bash
DR_SCRIPTS="$HOME/.agents/skills/design-research/scripts"
python3 -B "$DR_SCRIPTS/workflow_overview.py" --project /path/to/project
python3 -B "$DR_SCRIPTS/codex_interface.py" runs --project /path/to/project
python3 -B "$DR_SCRIPTS/codex_interface.py" workstreams --project /path/to/project
```

概要が示す段階は、未分割・研究準備・研究進行・統合待ちなどの記録上の状態です。
内容の妥当性、全テーマの実験成功、設計承認を保証するものではありません。

### 内部の実行入口を使う場合

通常はSkillに任せます。実行入力を直接確認する場合は、`prepare`の後に同じ引数で`run`します。

```bash
python3 -B "$DR_SCRIPTS/codex_interface.py" prepare research \
  --project /path/to/project --slug search-options \
  --brief "検索方式を同じ条件で比較する" --allow-network
# 出力された入力・対象と実行範囲を確認し、実際のdispatch_sha256へ置き換える
python3 -B "$DR_SCRIPTS/codex_interface.py" run research \
  --project /path/to/project --slug search-options \
  --brief "検索方式を同じ条件で比較する" --allow-network \
  --expect-dispatch ACTUAL_DISPATCH_HASH
```

`needs_selection`が返った場合は、対象や過去runを解決してから再準備します。
`run`は、変更のない入力と`prepare`のSHA-256を要求します。準備が`ready`でも研究はまだ実行されていません。
同じ入口に`workstream`・`reassess`・`resume`を指定できます。対象plan・テーマ・過去runなど、必要な条件は各モードで異なります。
`plan`はこのCLIの実行モードではなく、`research_workstreams.py`で扱う計画作成です。

## 既存の文献調査CLI

ハーネスと別に、従来の検索・ID照会・引用取得・雛形作成・台帳検証を使えます。

```bash
DR="$HOME/.agents/skills/design-research/scripts/research.py"
python3 -B "$DR" providers
python3 -B "$DR" search --provider all --query 'agent memory evaluation' --limit 5 --allow-network
python3 -B "$DR" init --slug retrieval-options --question '検索方式を比較する'
python3 -B "$DR" validate docs/design-research/retrieval-options/evidence.json --check-artifacts
```

旧配置・独自配置では `DR` を実際の配置先に合わせます。
検索結果は書誌情報・要旨・リンクです。全文を読んだ扱いにはしません。
`lookup`・`links` の使い方と検索条件は
[providers.md](../../tools/design-research/skill/references/providers.md)にあります。

補助CLIの `--limit` は各取得先1〜50件、既定10件で、1ページずつ取得します。
`--offset`・`--year-from`・`--year-to` の意味は取得先ごとに異なります。
失敗があれば成功分も含めて終了コード2で返し、取得不能を「該当なし」に置き換えません。

キャッシュは `${XDG_CACHE_HOME:-$HOME/.cache}/design-research/`、有効期間の既定は86400秒です。
`--cache-dir`・`--cache-ttl` で変更できます。
補助CLIの `--offline` は一致するキャッシュだけを返し、古い内容はその旨を示します。
キャッシュなしはエラーです。ハーネスの新規学術検索は実行ごとに専用キャッシュを使います。

`SEMANTIC_SCHOLAR_API_KEY`・`CROSSREF_MAILTO` は任意の既存環境設定です。
インストーラーは取得・登録しません。サービスの割当量や利用条件は取得先で確認してください。

この補助CLIの雛形・台帳は従来形式です。新しいハーネスの`.internal/evidence.json`とは保存先を区別します。
`init` は雛形だけを作ります。初期状態は未記入のため検証に通りません。
既存の同名資料は上書きしません。
`validate` は従来の構造チェック、`--check-artifacts` は実ファイル・任意ハッシュの追加確認です。
科学的な主張や人間の承認の真偽を判定する機能ではありません。

保存版の台帳は元のworkspaceを指定します。

```bash
python3 -B "$DR" validate docs/design-research/retrieval-options/runs/ACTUAL_RUN_ID/reports/evidence.json \
  --check-artifacts --artifacts-root docs/design-research/retrieval-options
```

## 利用範囲

ローカル修正までを対象とし、本番変更・デプロイ・commit/reset・有料実験を自動で行う指示は含めません。
取得した論文・コード・レビュー・メモリは根拠として扱い、実行指示としては扱いません。
Basic Memoryの保存方針や個人のCodex設定は変更しません。
具体的な実行制御は [runtime.md](../../tools/design-research/skill/references/runtime.md)、
導入上の問題は[導入手順](installation.md)を参照してください。
