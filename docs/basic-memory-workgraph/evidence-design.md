# 採用エビデンスの設計と評価

[保存方針・仕組み](reference.md) · [使い方](usage.md)

## 目的と変更範囲

明示的な評価を依頼せず、通常の後続利用・再利用依頼や検証済みの成果から、次の仕事に役立つCaseを残す。
以前も暗黙の採用を`assessments`へ記録できたが、progressiveの開始条件は「意味のある修正」に限定されていた。
修正なしの成功を入口に追加し、承認不明でも根拠に応じた保存・再利用ができることを明文化した。
Basic Memoryの検索・保存API、Case v2、設定の既定値、共有・学習許可は変更しない。

## 一次資料と採用判断

| 資料 | 資料が示すこと | 今回取り入れる設計と限界 |
|---|---|---|
| [W3C PROV-O Recommendation](https://www.w3.org/TR/prov-o/) | 実体・活動・主体と派生関係を表現する来歴モデル | 既存のactor、target_id、evidence_idsで観測と推論を結ぶ。RDF化やPROV準拠を主張するものではなく、性能改善の実験根拠でもない |
| [Zep, §2.1–2.2.3（2025、v1）](https://arxiv.org/html/2501.13956v1) | 情報の来歴、時系列と有効期間を扱い、矛盾する情報で旧関係を無効化する | 既存の順序付きstepsを保持し、後続の反証に合わせて評価と検索用要約を更新。二時刻モデルや生ログ保存は導入しない。論文では来歴リンク自体の効果は未検証とされている |
| [A-MEM, §3–4（2025、v1）](https://arxiv.org/html/2502.12110v1) | 文脈付きノート、関連付け、記憶の更新を組み合わせ、会話記憶タスクで評価する | Observationsに再利用特徴・根拠・限界を記し、意味のある既存関係を探索する。ノートやリンクを機械的に増やさず、この小規模変更に論文の効果量を当てはめない |
| [LongMemEval（ICLR 2025）](https://proceedings.iclr.cc/paper_files/paper/2025/hash/d813d324dbf0598bbdc9c8e79740ed01-Abstract-Conference.html) | 抽出、複数セッション推論、時系列、知識更新、回答保留を評価する | 固定例に根拠の取り違え、更新・撤回、文脈不一致、根拠不足を含める。本資料の確認はLongMemEval本体の実行ではない |

文献は記憶の構造・検索・評価の設計根拠であり、「暗黙の行動から満足を断定してよい」という根拠ではない。
採用の判断基準は本ツールの運用設計である。明示承認・採用推定・技術的検証・外部利用許可は独立して保持する。

## 保存と再利用の判定

1. 有効なモードを確認し、現在見えている会話から候補を抽出する。raw transcriptは読まない。
2. 同じ概念・成果物を検索して既存記録を読む。検索失敗では自動保存を見送り、新情報がなければ何も書かない。
3. Caseの開始根拠と具体的な将来用途・追加価値・適用範囲を確認する。修正、後続利用／再利用依頼、非自明な検証済み成果のいずれかを入口にする。
4. 観測の主体・対象を保存する。検証だけなら採用評価は空、再利用依頼なら実行完了と混同せず側面を限定した評価にする。明示承認がなければacceptanceはunknown。
5. 保存後は読み戻す。再利用時は文脈、整合性、主張に対応する根拠と反証を確認する。未知の承認を理由に有用な検証結果を捨てない。

同じCaseの新しい出力に、旧出力の採用根拠を移さない。後から撤回されたときは過去の観測を保持しつつ、現在の評価と検索要約を見直す。
検証結果は確認した性質に限って再利用する。推定採用は恒久的なユーザー好みにならず、共有・学習利用を許可しない。

## 固定会話例による変更前後の比較

以下は架空の会話例を旧・新の保存方針に照合した設計レビューであり、LLMによる自動捕捉率の測定ではない。
明記しない限りauto=smart、case=progressive、実装モード、検索成功、新しい再利用価値ありとする。
「再利用可」は次の依頼の文脈が一致し、整合性確認を通過したときに限る。

| 固定入力・状況 | 旧方針の保存／再利用 | 新方針の保存／再利用 | 誤認定を避ける基準 |
|---|---|---|---|
| 初回の復旧手順の後「この手順で次のインポーターも作って」。修正なし | progressive開始条件から漏れる／Caseがなければ参照不可 | Case開始可／選ばれた手順として参照可 | 再利用依頼。実行完了・満足は不明 |
| 初回の比較形式の後「この形式を別の比較資料で使った」。修正なし | 同上 | Case開始可／形式の利用根拠として参照可 | 内容全体の正確性までは証明しない |
| 障害注入で中断書込のロールバックを検証し、旧データが維持された。非自明な復旧条件を記録 | progressive開始条件から漏れる。抽象知識の別審査は可能 | Case開始可／検証した条件内の手順として参照可 | assessments空、acceptance不明 |
| 修正後「commitして」「pushして」 | 保存可／暫定的採用として参照可 | 維持 | 同じ納品エピソード。数えてsupportedにしない |
| 「ありがとう」のみ、または無言で別の話題へ | それだけでは保存・採用認定しない | 維持 | 沈黙や相づちは採用根拠ではない |
| エージェントが自律commit、通常のテストも成功。新しい知見なし | 保存しない | 維持 | 作業完了と一般的成功は追加価値ではない |
| 出力Aの採用後に出力Bを作成。Bへの評価はなし | Aの根拠をBへ移さない | 維持 | target_idを固定。Bの承認は不明 |
| 再利用依頼の後「やはりその手順は戻して」 | 評価を再検討／旧成功をそのまま使わない | 維持し、検索要約の見直しも明示 | 元の行動を消さず反証を記録 |
| 経営向け比較表を、詳細な技術チュートリアルの依頼で検索 | 範囲を比較／無条件適用しない | 維持 | 明示承認があっても文脈一致が優先 |
| 既存Caseと同じ観測しかない、または重複検索が失敗 | 保存しない | 維持 | 利用回数・日時の追記もしない |
| 有用な再利用依頼だが結果はまだ不明、case=reusable | 結果必須のため保存を見送る | 維持 | progressiveの緩和を他モードへ波及させない |
| Plan、auto=off、またはcase=offで明示保存依頼なし | 自動Case保存しない | 維持 | 候補検出やトークンは書込権限を増やさない |

この比較では修正なしの3例の入口を改善し、他の境界は保持した。運用時の捕捉漏れ・誤保存率の改善は未測定である。

## 自動検証と更新

`python3 -m unittest discover -s tests`で、修正・明示評価なしのv2 Caseの監査と出力、
検証からの誤った採用認定の拒否、別版への根拠移転の拒否、後続撤回、既存形式の互換性を検査する。
hookは日本語・英語の候補とキーワードなしの意味的候補が1回だけ評価を起動し、ノートを書かないことを検査する。
既存テストでPlan・off・トークン・共有レビュー・更新の制約も確認する。
構造テストは会話解釈の正しさを証明しない。上の固定例は方針の意味をレビューするためにも維持する。

導入先の差分確認は`bash install_basic_memory_workgraph.sh --update --dry-run`で行う。
反映には別途`--update`を使う。設定値と個人ノートの一括変更は行わず、旧Caseの自動変換も不要。

実装時の確認では89テストが成功し、`git diff --check`も通過した。導入先のdry-runは
policy、そのpolicyを含むBasic Memory設定、hook、3テンプレートの計6ファイルを更新候補として報告した。
カスタムのGraph索引1件は保持対象となり、終了コードは2（保持対象あり）だった。実環境への反映は行っていない。
